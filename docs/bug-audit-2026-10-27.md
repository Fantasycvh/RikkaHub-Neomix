## 一、高严重度

### 1. 换库状态机不可恢复崩溃窗口(备份)【确认 ✅】

**位置**:`app/src/main/java/app/androidrik/rikkahub/data/sync/PendingRestoreStore.kt:114`(校验)、`:145-156`(换入序列)、配合 `RikkaHubApp.kt:149-153`

`applyIfPending` 的崩溃窗口覆盖只处理了「让位后、换入前」(`recoverRollback`)与「marker 写完、pending 未清」两种。但从 `DatabaseRestoreFiles.moveIntoPlace(staged, databaseFile)`(行 145,move 语义,`staged.db` 源文件消失)到 `writeSynced(applied.marker)`(行 152)之间进程被杀/掉电时,下次启动 `hasPending=true`、`hasApplied=false`,行 114 的 `check(staged.isFile ...)` 抛 "Pending database is missing or incomplete" 并**永远复现**:磁盘上旧库其实完好(`recoverRollback` 已把它移回原位),但代码不会因此清 marker。结果:gate 屏每次显示 Failed(canRetry=true),重试永远抛同一异常,用户被永久挡在启动屏,只能清应用数据。

附带:行 201-206 只对 marker 文件做了 `fd.sync()`,payload 的 rename 未 fsync——掉电时同样可能出现「marker 在、payload 丢」。

**修复建议**:行 114 校验 staged 缺失时,若 rollback 副本完好应清 pending 转正常启动;换入序列前后补 payload fsync。

### 2. `loadMessageNodes` 跳页 + 增量保存删除链 → 不可逆数据丢失(数据层)【确认 ✅】

**位置**:`app/src/main/java/app/androidrik/rikkahub/data/repository/ConversationRepository.kt:896-913`(catch 分支)+ `:956-978`(`saveMessageNodes`)

- `loadMessageNodes` 捕获 `SQLiteBlobTooBigException` / `IllegalStateException` 后 `offset += pageSize; continue`,把**整页(最多 64 个节点,含好节点)静默跳过**,内存中的节点序列因此缺失。
- `saveMessageNodes` 以「内存列表 ≡ 全量」为不变量求公共内容前缀;缺失处签名不匹配 → `common` 停在该下标 → `deleteFromIndex(common)` 把库中该超大节点**及其后所有行删掉**再按内存重插。

即:用户打开一次含超大节点(单节点 messages JSON 超出 SQLite cursor 窗口,约 2MB)的会话并发一条消息,该节点及后续内容被不可逆删除。仓库注释(repo:933-936)证实存在 16MB 级会话,现实可触发。

**修复建议**:catch 分支改为按主键跳过单行(而非整页);`saveMessageNodes` 检测到内存序列比库中少行时拒绝本次增量删除(或对 skip 事件打标记禁用增量写)。

### 3. `encodeBase64` 双缺口,图片回传三家全中招(ai)【确认 ✅】

**位置**:`ai/src/main/java/app/androidrik/ai/util/FileEncoder.kt:105-135`;调用方 `ClaudeProvider.kt:519`、`GoogleProvider.kt:744`

- `data:` URL 分支(125-129 行)**无视 `withPrefix`**,永远返回完整 data URL。Claude `toContentBlock` 与 Google `toGooglePart` 均以 `withPrefix=false` 调用并把返回值直接放进 `data` / `inlineData.data` 字段 → 发出 `"data:image/png;base64,..."` 而非裸 base64,服务端必拒。
- **没有裸 base64 分支**:Google `parseMessagePart` 把 Gemini 返回的 `inlineData.data`(裸 base64)存进 `Image.url`,下轮请求时 `encodeBase64(false)` 落到 `else -> throw` 分支 → 图片被静默从上下文丢弃(Claude 侧换成空文本)。app 层 `Base64ImageSanitizer` 只认 `data:` 前缀,救不了这个形态。

触发场景:模型输出图片(Gemini 生图 / OpenRouter 图片模态)+ 下一轮带图重发。

**修复建议**:`data:` 分支剥离前缀返回裸 base64;新增裸 base64 直通分支(按 mime 校验)。

### 4. 文件工具 resolve-then-open TOCTOU 逃逸(workspace)【确认】

**位置**:`workspace/src/main/java/app/androidrik/workspace/WorkspaceFileSystem.kt:313-330`(`resolvePath`)及 `readText(:27-35)`、`writeText(:48-52)`、`move(:221-241)`、`delete(:182)`;`WorkspaceManager.kt:120-158`

`resolvePath` 用 `canonicalFile` 一次性解析符号链接并校验前缀,随后用返回的 File 直接 IO。`canonicalFile` 与实际 open 之间无锚定(无 openat/目录 FD),前台工具与**后台任务并行**的 shell 以同一 uid 完全控制 filesDir/rootfs,可在窗口内 `rm -rf a && ln -s /data/... a`,使后续 open 跟随符号链接逃出工作区根目录,绕过 `writableRoots` 审批层和 `/upload` 只读快照保护。

佐证:`importBytes`(:88-93、:147-152 注释)明确承认该窗口并做了部分缓解(`CREATE_NEW`+`NOFOLLOW_LINKS`、删除前 `isSafeToDelete` 复核),但 `readText`/`writeText`/`move`/`exportFile` 系列对同一窗口**无任何缓解**。触发需并发时序,定性"确认(窗口存在)/ 疑似(实际利用)"。

## 二、中严重度

### ai 模块

**5. Claude / ResponseAPI 流式 `onFailure` 中 `close(null)` 把失败当成功**【确认 ✅】
`ClaudeProvider.kt:272-277`、`ResponseAPI.kt:242-247`。当 `t == null`(HTTP 非 2xx)且错误体为空/解析失败时 `exception` 保持 null,`close(null)` = 正常结束:不触发重试路径、`finishIncomplete` 语义错乱。同仓 `ChatCompletionsAPI.kt:316-320` 已修同一问题并留注释,`GoogleProvider.kt:353` 也有 `exception ?: Exception("Stream failed")` 兜底,唯这两处漏。

**6. Google 图片输出模式丢弃 system prompt**【确认 ✅】
`GoogleProvider.kt:379-391`(systemInstruction 仅在无 IMAGE modality 时写入)+ `:678-683`(buildContents 对 firstSystem 无条件跳过防重复)。两条件叠加:outputModalities 含 IMAGE 时,第一条 system 消息既不进 systemInstruction 也不进 contents,无声丢失。

**7. ChatCompletions 流式 `"error": null` 杀死整条流**【代码缺陷确认,触发疑似 ✅】
`ChatCompletionsAPI.kt:256-259`。`if (it["error"] != null)` 是引用判空,kotlinx 的 JSON `null` 是非空 `JsonNull` 引用 → 网关下发 `"error": null` 表示"无错误"时会进错误分支,`parseErrorDetail()` 落 else 产出 `HttpException("null")`。同仓 `ResponseAPI.parseStreamFailure` 的 `takeIf { it !is JsonNull }` 已正确处理,此处漏。

**8. 流式 Image delta 双重前缀拼接**【确认】
`ai/ui/Message.kt:89-103` 的 `appendChunk` Image 分支假设 delta 是裸 base64 片段,而 `ChatCompletionsAPI.parseMessage`(`:951-971`)存入的是完整 URL(原样存)。两约定冲突:网关流式回图时生成 `"data:image/png;base64,data:image/png;base64,..."`;两张图连续到达还会直接字符串拼接。

**9. Responses API `function_call_output` 双事件各追加一次**【合并语义确认,触发疑似 ✅】
`ResponseAPI.kt:691-693`(output_item.added)与 `:780-782`(output_item.done)都会对 `function_call_output` 发 chunk,经 `Tool.merge`(`UIMessagePart.kt:176-187`,`output = output + other.output`)拼接 → 工具输出双份,回传下轮上下文翻倍。标准 Responses 流两个事件都携带完整条目时必触发。

**10. Google 非流式阻断响应 `!!` 硬解**【确认】
`GoogleProvider.kt:208-209`(`candidates!!`、`usageMetadata!!`)、`:558`(`error("No content")`)。Gemini 被 prompt 阻断时只有 `promptFeedback` 无 `candidates`,直接抛 NPE 而非上报 blockReason(streamText 路径 `:270-273` 有处理,非流式没有)。
