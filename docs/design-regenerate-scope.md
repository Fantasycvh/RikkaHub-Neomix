# 重生成语义：scope 可选 + 撤销（设计稿）

> 状态：**已实现（`ad3543b2`），真机验证通过**（2026-09-15）。决策见 §三。
> **实现结果**：`RegenerateScope{THIS_ONLY, INCLUDE_FOLLOWING}`（不按角色）+ 仅 B 确认（含「先导出再继续」）+ 截断后「已移除 N 条 · 撤销」；纯函数抽到 `data/model/RegeneratePlan`（单测 14 项 + 检查点交叉 1 项）；死参数 `regenerateAssistantMsg` 已清。默认 scope 仍为 INCLUDE_FOLLOWING，web/API 调用方行为不变。
> **§五 的冲突处理**：实现取「撤销覆盖已生成」——`undoRegenerateTruncation` 先 `stopGeneration` 再 `take(截断后长度)` 拼回尾巴（截断后新产生的回复与 #1812 半截草稿一并撤掉 = 回到截断前）；**用户已手动验证通过**。
> 关联：`design-auto-compaction.md`（检查点失效）、`design-compress-presets.md`（同为压缩线）。

## 一、现状核实（两种角色已经不对称）

| 重生成对象 | 被重生成的那条 | 下游 |
|---|---|---|
| **助手消息** | 旧回答**保留**为同节点候选（`updateCurrentMessages` append + 切 `selectIndex`）= **已在分支里** | **保留**（不动） |
| **用户消息** | 用户消息本身不变（无新候选） | **硬删除**（`subList(0, indexAt+1)` → `saveMessageNodes` 的 `deleteFromIndex` 落库） |

所以「重生成前的内容落在其分支」**助手侧已成立**；真正无归宿的是**用户重生成时被删掉的尾巴**。

**关键发现（支持"不按角色区分"）**：`editMessage`（`ChatService.kt:1399-1432`）只给该节点**追加候选并切换选中**：

```kotlin
node.copy(messages = node.messages + UIMessage(role = node.role, parts = processedParts),
          selectIndex = node.messages.size)
```

**完全不碰下游。** 即「编辑后下游回答处于旧语境」这个错配**在编辑那一刻就已产生**，与重生成无关。故：

- 提示文案的判据应是「**是否编辑过**」而非角色；
- 两种 scope 都是正当需求，凭角色决定哪个可用是任意的。

**顺带发现（可清理）**：`regenerateAtMessage(message, regenerateAssistantMsg)` 的第二参数是**死参数**——两个调用方（`ChatPage.kt:476`、`ConversationRoutes.kt:346`）都用默认 `true`，`else` 分支的 `saveConversation` 不可达。

## 二、两种 scope 的定义

| scope | 语义 | 性质 |
|---|---|---|
| **A. 仅本条与对应回复** | 只重做这一段，**容忍**下游已有的错配 | 非破坏 |
| **B. 含后续所有对话** | 从这里重做，**丢弃**下游（错配随之消失） | 破坏 |

两个原语都已存在：**截断**（用户路径现成：`subList` + 落库）与**候选追加**（助手路径现成：索引映射写回）。
故 A/B 不是"实现两种 scope"而是"**让 scope 可选、而非由角色决定**"——交叉套用即可。

例：**用户消息的 scope A** = 把 `subList(0, indexAt+1)` 换成 `messageRange = 0..<(indexAt+1)`，
新回复作为候选落到 node k+1，形状与助手路径几乎相同。

## 三、已定决策（2026-09-15）

| # | 决策 | 说明 |
|---|---|---|
| 1 | **不按角色区分 scope** | 用户编辑后是想"只修正这一段"还是"从这里重做"，与消息角色无关 |
| 2 | **只在 scope B 要求确认** | B 破坏性、A 非破坏；确认文案可直接用上游 `d47d13a6` 那版（"此消息下方所有消息会被删除"） |
| 3 | ~~自动分支对话~~ → **改为 snackbar 撤销** | 见 §四 的理由（fork 的代价） |
| 4 | **B 的确认弹窗里提供「导出后继续」** | 见 §六：**导出能"留存"但不能"回退"**，但它让用户能在截断前先留一份 → **§五 的纠缠由此基本消解** |

## 四、为什么放弃"自动分支"，改用撤销

**自动分支实现便宜**（复用 `forkConversationAtMessage`：截断前先复制前缀到新会话），但核实出两项代价：

1. **附件被物理复制**：fork 走 `createForkConversation` → `copyWithForkedFileUrl` →
   `createChatFilesByContents`，后者**逐字节拷贝文件**（`FilesManager.kt:112-130`）。
   带图会话自动分支一次 = **磁盘上图片翻倍**。这是 fork 的固有设计（刻意复制以使两会话文件
   生命周期独立，`deleteConversationFiles` 依赖此），不能顺手改掉。
2. **fork 不复制压缩检查点**：`createForkConversation`（`ChatService.kt:143-155`）只搬
   `messageNodes` 等字段，**未搬 `compressionSummaries`**（默认空）→ 副本丢掉压缩状态、重发全量历史。

次要代价：会话列表膨胀（有界，见 §六）、FTS/备份随之增大。

**另一项相互作用**：若 B 自动分支（=不丢数据），确认弹窗的性质会从「**警告数据丢失**」变成
「**告知已建副本**」——两者**部分互相替代**，不该同时上（用户点两次只得一件事）。

**撤销方案**：沿用现有 snackbar 模式（`HistoryPage.kt:105-136` 删会话即"内存持有 → 删除 →
撤销则还原 / 否则清理文件"）。截断把尾巴**留在内存**、弹「已移除 N 条 · 撤销」，
撤销 = 取消在飞生成 + 还原尾巴。

**取舍本质**：**要「后悔药」用撤销（便宜：无 schema、无附件复制、无列表膨胀）；
要「两条时间线都留」才需 fork（贵）**。本次选撤销。

## 五、待解决的实现冲突（动手前必须定）

**问题：截断后立即生成，会把"撤销"变得难以正确实现。**

用户消息的 B 路径当前是：`subList(0, indexAt+1)` → `saveConversation` → `handleMessageComplete`
（**立刻开始生成新回复**）。而新的回复会**追加为新节点**。

于是"撤销"要还原的不只是被删的尾巴，还要**撤掉刚生成的新回复**——即：

- 按 node id 还原尾巴时，新回复已占用了下标 → **必须先把新回复删掉再插回尾巴**，
  或用 id 感知的合并逻辑（不能简单拼接列表）；
- 而"取消在飞生成"（`stopGeneration`）与"还原"之间有时序窗口：生成可能已产出半截内容。

**三种处理方式**（需选一）：

| 方式 | 说明 | 代价 |
|---|---|---|
| **a. 撤销仅覆盖"未生成"窗口** | 截断后先不长条链（或长条链在生成开始后不可撤销），撤销只针对纯截断 | 最简单、语义干净；但用户常在生成中才后悔 |
| **b. 还原 = 取消生成 + 删新回复 + 插回尾巴** | 完整语义 | 需按 node id 合并、处理半截输出（与 #1812 草稿机制交叉） |
| **c. 弹条链时先不生成，等条链消失再生成** | 用条链的 5s 窗口"替代"确认弹窗 | 改变现有交互节奏，且生成延迟 5s 不可接受 |

**建议 a**（先做最小正确版本）：截断→弹条链；**若用户此时已触发生成，条链的撤销改为禁用/降级**
（只提示"已移除 N 条"）。这样避免与生成回路、#1812 草稿、节点索引三方纠缠。

**§5.1 的替代/补充：确认弹窗里给「导出后继续」（见 §六）可整个消掉本节的纠缠**——
用户既有机会事前留存，就不必在内存留尾巴、也不必处理"撤销还要撤新回复"。

## 六、"提示用户导出后回退"的评估（2026-09-15 增补）

**结论：导出能"留存"，但不能"回退"——两者不可互相替代。**

### 6.1 关键事实：导出的落点是临时文件 + 分享面板，启动即清

`exportToMarkdown`（`Export.kt:413-430`）的落点是 `context.appTempFolder`（**临时目录**）
→ `FileProvider` → `shareFile()`。而 `RikkaHubApp.deleteTempFiles()` **每次启动
`deleteRecursively()` 清空该目录**（`RikkaHubApp.kt:145-152`）。

所以导出的语义是：**生成一个临时文件并交给系统分享面板**。用户没在分享面板里真正落到
某处，**下次启动就没了**。且全仓**没有任何"从导出文件回填会话"的路径**
（`ChatboxImporter` 只导外部 chatbox 格式，不是回填同一会话）。

**故「导出后回退到重生成前」字面上不成立**——导出给的是「App 外的一份副本」，
不是「能回到原状态」。要真回退只能靠 in-app 机制（撤销或归档）。

### 6.2 两种读法（都成立，但只有一种能消掉 §五）

| 读法 | 时机 | 导出对象 | 效果 |
|---|---|---|---|
| **A. 事前** | 截断**前** | 即将被删的**尾巴** | 「想留就先存」→ **整个消掉 §五** |
| **B. 事后** | 生成**后** | **新生成的回复** | 回退前先把新版存下来 |

### 6.3 三种机制的性质对比（不重叠，各据其位）

| | snackbar 撤销（in-app） | 导出（external） | 归档（in-app，未设计） |
|---|---|---|---|
| 结果 | **原位还原成原状态** = 真可逆 | App 外一份副本；**回不到会话里** | 原位可查看/恢复 |
| 时效 | 条链存续期（秒级） | 文件在就在；**临时目录启动即清** | 持久 |
| 与生成回路耦合 | **有**（§五：还需撤新回复） | **无**（纯读，任何时刻可做） | 有（位置冲突） |
| 覆盖范围 | 只有最近一次操作 | **任意子集**（导出已支持 `selectedMessages: List<UIMessage>`） | 特定截断点 |
| 成本 | 低-中（§五 纠缠） | 低（复用现成三形态导出） | 中（schema + 渲染/窗口/FTS 排除） |

**关键差异：撤销解决「我手滑了」，导出解决「我想留一份」。** 导出**无法**覆盖手滑
（必须在删除前发生），撤销**无法**覆盖「想长期留存」（秒级窗口）。

### 6.4 建议（都做，但都做最简）

1. **确认弹窗里给「导出后继续」**（读法 A）——**整个消掉 §五 的纠缠**：
   用户既有机会事前导出，就不必在内存留尾巴、也不必处理"撤销还要撤新回复"。
   成本几乎为零（复用现成导出三形态，且导出接受任意消息子集）。
2. **撤销条链只做「未生成窗口」**（§五 的选项 a）——保留覆盖手滑场景。
   若决定完全不做撤销也可接受，但要清楚**手滑将不可恢复**。
3. **导出 ≠ 回退**，所以**不要**用"导出"文案承诺可回退（如"导出后可回退"是错误表述）；
   应表述为「**导出后继续**」（=先留副本再截断）。

### 6.5 若要「真·回退」（in-app 可恢复）→ 归档而非导出

给被截断的节点打「已归档」标志（不参与 `currentMessages`/发送窗口/渲染/FTS），
在截断点放一行「已归档 N 条 · 查看/恢复」。性质：**持久**（不像撤销靠内存）、
**原位可恢复**（不像导出离开 App）；但**成本中等**（动渲染 + `currentMessages` +
发送窗口须排除归档 + FTS/导出），且"生成已追加新节点"时仍有位置冲突（需挪位）。

**轻重排序：撤销（最轻）< 归档（中）< fork（最重，附件复制 + 副本丢检查点）**。

**注意 scope A 不需要撤销**（非破坏）——它只需一个提示文案（下游是旧语境产物）。

## 七、其它已核实的事实

- **检查点失效已自动覆盖**：区域指纹（`bbba9ba8`）按「区域内节点 id + 选中消息 id」的 SHA-256
  判定；用户分支 `subList` 截断后 `boundaryNodeId` 指向的节点消失即失效；
  `CompressionWindowTest` 已有 `regenerating a node within area invalidates checkpoint` 用例
  （构造新候选 + 切 `selectIndex` → 断言失效）。
- **⚠️ 三处文档过时**：`handoff-2026-09-04.md:74`、`roadmap.md:556/558` 仍写
  「已知限制：重新生成边界内消息未触发失效（影响微妙）」——该限制写于**指纹校验之前**，
  `bbba9ba8` 已覆盖，属**假限制**，会误导后续排查，应清理。
- **会话列表膨胀有界**：同一截断点重复操作时下游已空，无需再截断。
- **`saveMessageNodes` 用公共前缀 diff**（`ConversationRepository.kt:602-624`）：
  截断（缩短）走 `deleteFromIndex`；还原（变长/变化）走插入——故"还原"是 DB 层支持的。
- **`currentMessages` 是索引映射**（`Conversation.kt`），`updateCurrentMessages` **索引对齐写回**
  是生成回路的核心机制——任何"重排节点列表"的方案都要过这一关（这也是不做树模型的原因）。

## 八、成本

| 项 | 量级 |
|---|---|
| scope A/B 参数 + 两分支交叉套用 | 低 |
| 确认弹窗（仅 B）+ 文案（用上游那版） | 低 |
| 撤销条链（含 §五 选定方式） | 低-中（取决于选 a 还是 b） |
| 清 `regenerateAssistantMsg` 死参数 | 极低 |
| 单测（scope 交叉、撤销还原、检查点失效交叉） | 低 |

**合计约 1–2 提交**（按 §五 选 a 则靠近 1 个）。

## 九、不做

**同会话内"尾部落成分支"（树模型）**——线性 `messageNodes` 加分支只能是"同位置多候选"，
没有"路径"表示；改造需动 103 处引用与索引对齐写回/前缀 diff/边界索引等核心不变量，
**架构级（数周）**，与收益不成比例。保留需求走本设计的撤销，或用户显式用现有 fork。
