# 压缩参数可配置化 + 压缩配置档（设计稿）

> 状态：**已实现并真机验证**（`33c2978c`，2026-09-15）。五项决策见 §二。
> **实现结果**：设置页档选择器 + 数值输入、档管理（增/改/删）、手动对话框初值读设置且无阈值；单测 +14；app 480 项仅 `MarkdownMathParse` 既有失败。
> **实现期发现并修复的缺陷**：「自定义」原实现为 onClick 为空的 `FilterChip` = **死点击**。按设计（真相源是数值）它没有任何值可改、本质是**状态指示**，已改为标签行文字后缀（仅在数值不匹配任何档时出现）。
> 关联：`design-auto-compaction.md`（压缩机制本体）、`roadmap.md`。

## 一、现状核实（与原始提案的出入）

**"三个固定值"并不完整——只覆盖自动路径的一半，手动路径是硬编码的。**

| 参数 | 自动压缩 | 手动压缩（`CompressContextDialog`） |
|---|---|---|
| 触发阈值 `thresholdPercent`（默认 80） | ✅ 读设置（`ChatService:1245` 附近） | — 不适用（手动由用户点击触发） |
| 保留比例 `retainPercent`（默认 40） | ✅ 读设置 | ⚠️ **对话框内硬编码** `remember { mutableIntStateOf(40) }` |
| 摘要目标 `targetTokens`（默认 2000） | ✅ 读设置 | ⚠️ **对话框内硬编码** `remember { mutableIntStateOf(2000) }` |

现有选项列表（均在 UI 层硬编码，非持久化）：

- 设置页自动压缩：`thresholdOptions = [60,70,80,90]`、`retainOptions = [20,30,40,50,60]`、`targetTokenOptions = [1000,2000,4000,8000]`
- 手动对话框：`tokenOptions = [500,1000,2000,4000]`、`retainOptions = [20,30,40,50,60]`

**两个既存问题（顺带修）**：

1. 手动对话框每次打开都重置为 2000/40——**上次选的参数不被记住**；
2. 两条路径的参数互相独立、无关联，同一个概念（"压成什么样"）有两份来源。

**已有的正确基础**：三个值**已经**在 Settings 里且三件套齐全（`PreferencesStore:502-505`、`:678-688`），所以**持久化无需改动、零迁移**。

## 二、已定决策（2026-09-15）

| # | 决策 | 说明 |
|---|---|---|
| 1 | **三个数值是唯一真相源**；"档"只是填充数值的快捷方式 | 压缩行为只由三个数值决定，档不参与运行期逻辑 |
| 2 | 提供**自定义档的创建/修改/删除**；临时数值不持久化 | 用户可把自己的方案固定下来并反复使用 |
| 3 | **阈值只属于自动压缩**；手动只暴露保留比例 + 摘要目标 | UI 按路径分组，避免误导手动也会用阈值 |
| 4 | **档只携带 2 个数**（保留比例 + 摘要目标），**不含阈值** | 见 §四：阈值是"何时压"的策略、非"压成什么样"的方案 |
| 5 | 边角规则见 §六.2 | 内置档不可删 / 阻止重名 / 允许数值重复 / 自定义档上限 20 |

**决策 3 与 4 的根据（用户 2026-09-15 补充，比原判断更准确）**：手动压缩的触发条件**就是用户自己的判断**——"因为上下文达到某个值或觉得过长时才进行的"。所以阈值对**手动根本不构成一个概念**（不只是"不暴露"）：既然触发由用户决定，就不存在"何时触发"这个参数。由此档只应携带"压成什么样"的 2 个数。

**决策 1 的一个重要收益（删除安全）**：因为真相源是数值而非"当前选中的档"，**删除任何档都不会改变当前压缩行为**。删除是纯 UI 操作，无副作用——这让档的管理 UI 可以做得很简单。

## 三、数据模型

```
Settings（顶层）
├─ autoCompressThresholdPercent: Int   ← 已有，真相源之一
├─ autoCompressRetainPercent:    Int   ← 已有，真相源之一
├─ autoCompressTargetTokens:     Int   ← 已有，真相源之一
└─ compressPresets: List<CompressPreset>   ← 新增（仅自定义档）
```

- **内置档**用常量表示（不持久化、不可删），与 `DEFAULT_MODE_INJECTIONS` 同风格；
- **自定义档**存 `Settings` 顶层 `List<CompressPreset>`，持久化写法**复用现有列表模式**（单 string key + JSON），与 `modeInjections`/`lorebooks`/`customThemes` 完全一致：
  ```
  key:  stringPreferencesKey("compress_presets")
  读:   preferences[COMPRESS_PRESETS]?.let { JsonInstant.decodeFromString(it) } ?: emptyList()
  写:   preferences[COMPRESS_PRESETS] = JsonInstant.encodeToString(settings.compressPresets)
  ```
  （`CompressPreset` 为 `@Serializable`，故是**一个 key 装 JSON 列表**，不是三个 key。）

**兼容性**：新字段默认 `emptyList()` + `ignoreUnknownKeys` → 旧设置/旧备份直接解码，**零迁移**。

## 四、档的形态与选中判定（决策 4 已定）

**档只携带两个数值**：`CompressPreset(name, retainPercent, targetTokens)`——即"压成什么样"。

理由：阈值回答的是"**什么时候**压"（自动专属的触发策略，与设备/模型上下文相关），而保留比例与摘要目标回答"**压成什么样**"（方案本身，跨路径通用）。**手动压缩的触发条件本就是用户自己的判断**（觉得长/快满了才点），阈值对它是概念上不存在的参数（决策 3+4）。

**选中态用"数值推导"而非额外字段**：不存 `selectedPresetId`，而是**当数值恰好匹配某档时高亮该档**，否则显示为"自定义"（自动路径比 3 个数、手动路径比 2 个数）。

好处：无额外状态可与数值失同步（决策 1 的直接推论）。用户改一个数字，档位高亮自动变为"自定义"——语义正确且零维护。副作用：两个档数值相同时按首个匹配（可接受，见 §六.2）。

## 五、UI 与实现要点

**设置页（自动压缩块）**：档位选择器（内置档 + 自定义档 + "自定义"）+ 阈值/保留/目标三个数值控件（保留现有 SegmentedButton 快速档，并在"自定义"下换成数值输入）。**沿用现有 `IntRange` 钳制**：

- `AUTO_COMPRESS_THRESHOLD_PERCENT_RANGE = 50..95`（注释明写：避免误配置导致抖动或永不触发）
- `AUTO_COMPRESS_RETAIN_PERCENT_RANGE = 10..80`

**手动对话框（`CompressContextDialog`）**：只暴露保留比例 + 摘要目标，**初值改读当前设置**（顺带修掉"每次重置"的问题）；可选用当前档位作初值，并支持**一次性临时覆盖（不持久化）**。

**档的管理 UI（本次主要工作量）**：增/删/改名。可直接复用 `SettingThemePage` 里 **`CustomThemeItem` + `CustomThemeEditSheet` + onDelete** 的成熟形态（自定义主题就是"用户命名的列表项 + 增删改"，同构）。

**字符串**：6 语言（档名、内置档描述、"自定义"、数值输入 label/提示、校验错误）。

## 六、边角规则（决策 5 已定）

**6.1 档携带 2 个数（保留 + 目标），不含阈值** —— 已定，理由见 §四（阈值是"何时压"的策略，手动路径上它根本不构成概念）。

若将来有人想改回 3 个数，必须守住约束：手动应用档时**只写它暴露的两个字段**，不能顺带改阈值——否则用户在手动对话框里的操作会静默改变自动压缩的触发点。**这也是不该带阈值的原因**：让"不可能出错"比"出错时检查"更可靠。

**6.2 边角规则（已定）**：

- **内置档不可删**（始终留合理回退）；
- **阻止重名**（否则档位选择器出现两个同名项）；
- **允许数值重复**（高亮按首个匹配，可接受，不做特殊处理）；
- **自定义档上限 20**（防 UI 过长）。

## 七、成本与风险

**成本：中-低（约 1–2 提交）**，分项：

| 项 | 量级 | 说明 |
|---|---|---|
| 数据模型 + 三件套 | 极小 | 复用 `modeInjections` 同款写法，无迁移 |
| 档解析/匹配纯函数 | 小 | 可单测（含"数值推导高亮"的边界） |
| 设置页 UI | 中 | 档选择器 + 自定义数值输入 |
| **档管理 UI（增删改）** | **中（本次大头）** | 复用 `CustomThemeItem`/`EditSheet` 形态 |
| 手动对话框改造 | 小 | 初值读设置 + 分组 |
| 字符串 6 语言 | 小 | ~10 key |

**风险**：

1. **dummy settings 坑**（`settingsFlow.value` 在 DataStore 加载前是全默认）——档解析**只在 UI/VM 层做**，不要放进早启动路径，否则会拿到 80/40/2000 的假值判定"当前是默认档"。
2. **别把档当真相源**——否则需写迁移，且用户手改的值会被档覆盖。
3. **手动的临时覆盖不要持久化**（决策 2 已定），避免"随手调一次"污染全局。

**附带收益**：手动压缩对话框的参数不再每次重置为 2000/40。

## 八、结论

- **价值**：中——把对话框里的硬编码参数变成可配置，并统一两条路径的参数来源；
- **成本**：中-低（约 1–2 提交），**无迁移**（持久化基础已就绪），主要工作在档管理 UI（有 `SettingThemePage` 的成熟形态可复用）；
- **状态**：五项决策全部已定，**无阻塞项**，按本文档即可开工。
