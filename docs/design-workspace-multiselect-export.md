# 工作区「长按多选导出」评估（设计稿）

> 状态：**📝 评估 / 仅设计（2026-09-26）——未立项、未实现。** 本文只固定「现状核实 → 方案分档 → 待拍板」，实现前需重新核实代码。
> 一句话结论：**技术上很便宜（选择态本仓已有现成交互 + 文件系统是普通目录）；决策已定（§六：打包为可选项 + 同批做批量删除 + 首版禁用 LINUX 区），首版范围 = FILES 区多选 + 两种产物 + 批量删除（约 2 提交）**；另有一件事必须诚实标注：**folder 现在根本导不出来**，所以这个需求实际上同时补上了一个既存缺口。

## 一、需求

工作区文件管理器里**长按文件卡片 → 进入多选 → 批量导出**（"工作区长按多选导出"）。

## 二、现状核实（代码事实）

| 事实 | 位置 | 对本需求意味着什么 |
|---|---|---|

## 三、方案分档

### 档 1（小，推荐首版）：FILES 区多选 → 打包 zip 导出

- 交互：长按任一文件/文件夹 → 进入选择态（`ListSelectableItem` 同款 Checkbox + 底部浮动工具条：**取消 / 全选 / 导出(N)**）；选择态下点击卡片 = 切换选中（**不再进目录**），返回键先退出选择态。
- 导出：`CreateDocument("application/zip")` → 默认名 `<当前目录名>.zip`（根目录时 `workspace-<yyyyMMdd-HHmm>.zip`）→ **流式**写 zip（不落临时文件，直接写 SAF 的 `OutputStream`）。
- zip 内路径：**相对当前目录**（`a.txt`、`sub/b.txt`），不带绝对路径也不带 `../`（安全 + 可读）。
- 文件夹可被选中：递归打包为目录条目（含空目录）。
- 归属：**FILES 区**；LINUX/rootfs 区首版**禁用（按钮置灰 + 说明）**——理由见档 3。

### 档 2（中）：批量删除 + 逐个导出到目录

- 批量删除：复用同一套选择态，确认弹窗沿用 `workspace_detail_will_delete`（单删已有该弹窗），并显示"N 项 / 共 X MB"。
- 逐个导出到目录：新引入 `OpenDocumentTree` + `takePersistableUriPermission`，把选中项**按原目录结构**写进授权目录（适合"导出到相册/U 盘"这类场景）。**这是本需求唯一需要新平台能力的地方**，也是 SAF 授权管理的长期成本（授权失效、跨设备不可携带）。

### 档 3（大）：LINUX（rootfs）区多选导出

rootfs 是**普通目录**，技术上能遍历，但：树可能几万文件 / 数 GB、含符号链接与特殊文件、且 rootfs **在备份里本来就是被排除的**（可重装）。真要支持，得先回答"打包什么/排除什么"（等价于给 rootfs 定一套 tar 排除表），收益远低于成本。**建议首版明确不做**，并在 UI 上给出原因（不是"没实现"，而是"rootfs 不进导出"）。

## 四、成本与工作量

| 档 | 内容 | 估算 | 主要工作量 |
|---|---|---|---|
| 1 | 选择态 + zip 导出 | **≈1 提交** | 选择态 UI（照抄现成形状）+ 一个纯函数「选中集 → zip 条目计划」+ 流式写出 + 6 语言字符串若干 + 单测 |
| 2 | 批量删除 + 目录授权逐个导出 | ≈1 提交 | 删除几乎零新增；目录授权那部分是新平台面（授权、冲突策略、部分成功的失败清单） |
| 3 | rootfs 导出 | 需先定排除策略 | **首版禁用并说明**（见 §六.4） |

**按 §六 决议，首版 = 档 1 + 档 2（约 2 提交），仅 FILES 区。**

**纯函数可单测的部分**（建议同批做）：条目计划（选中的文件/目录 → 条目名列表 + 空目录条目）、相对路径归一（拒绝 `..` 与绝对路径）、大小汇总（用于"共 X MB"与上限提示）、默认 zip 名生成。

## 五、风险与注意点

1. **OOM / ANR**：大目录必须**流式** + `Dispatchers.IO` + **可取消**（本仓有"主线程文件 IO 直接 ANR"的前科，`ConversationArchive` 那次）。压缩比未知 ⇒ 不做"先压到 cache 再上传"。
2. **路径逃逸 / zip-slip**：条目名只能来自 `WorkspaceFileSystem.resolve` 之后的**相对**路径；写入目录授权时同样要防 `..`。已有拒绝 zip-slip 的先例可照抄判据。
3. **选中态与导航的交互**（易被忽略）：选择态下 **进目录要禁用**（点击改为切换选中），否则"跨目录选择"这个语义会立刻出现（是否允许？跨目录导出时的相对路径基准是谁？）。**建议：切换目录一律清空选择，明确不做跨目录多选**。
4. **隐藏手势的发现性**：本仓有过"图标-only 入口不可发现"的教训（测试连接按钮）。长按是**没有视觉提示**的手势 ⇒ 建议：(a) 选择态工具条按钮全部带文字（不只图标）；(b) 顶部栏已有 `⋮` 的情况下，把"多选"也放进 ⋮ 菜单作为等价入口（**双入口**，长按只是快捷方式）。
5. **大体积提示**：选中集超过阈值（建议 **200MB 或 2000 个条目**）先弹确认（"共 X MB / N 项，导出可能较慢"），而不是直接开跑——沿用备份"先求和再提示"的手法。
6. **与 `design-side-file-panel.md` 的联动**：那份设计计划把文件浏览器抽成**共享组件**（详情页 + 侧边栏两处复用）。选择态**不要塞进共享组件的内部状态**，应由宿主 VM 持有、组件只接收 `selecting/selectedKeys/onSelectChange`（`ListSelectableItem` 现在就是这个形状 ✓）——否则抽取共享组件时两边会再次分叉。
7. **文件名冲突**：zip 内同名由"相对路径"天然区分；写入目录授权时若目标已存在，需要定策略（覆盖/跳过/重命名）——档 2 的待定项。

## 六、2026-09-26 决议（用户已定）

| # | 议题 | 决议 |
|---|---|---|
| 1 | 产物形态 | **「打包」作为可选项**——导出时给两种产物：**打包为 zip（一个文档）** / **逐个导出（多文件）**。见 §6.1 |
| 2 | 批量删除 | **同批做**（选择框架边际成本极低，删除已支持 `recursive`，逻辑侧零新增） |
| 3 | 空目录 | **保留在 zip 里**（更忠实；实测成本 = 遍历时把目录条目也写进 zip）——**本条用户未表态，按推荐默认值锁**，翻案成本极小 |
| 4 | LINUX 区 | 首版**禁用并给出说明**（不是"没实现"，而是"rootfs 不进导出"：树可能数 GB、含特殊文件，且它在备份里本就排除） |

### 6.1 「打包」作为可选项 ⇒ 目录授权进首版（成本随之上升）

原档 1 只做 zip，所以只需 `CreateDocument`；现在"逐个导出"要落成真实能力，**必须新引入
`OpenDocumentTree` + `takePersistableUriPermission`**（全仓首次使用），把选中项按**原目录结构**
用 `DocumentFile` 写进授权目录（Android 11+ 允许建子目录）。因此：

- 成本从「档 1 ≈1 提交」变成 **「档 1 + 档 2 ≈2 提交」**（主要增量是目录授权的流程与失败清单，不是遍历本身）。
- **一个让"可选"更自然的细节**：选择**恰好一个文件**时，"打包"是多余的——此时直接走既有的
  `CreateDocument` 单文件导出（等价于现在的行为，零新增概念）；**多选或含文件夹**时才需要在
  「打包为 zip（默认预选）」与「逐个导出到目录」之间二选一。
- **两种产物的失败语义不同，必须分别交代**：zip 是单文档（失败 = 一个都不成），
  逐个导出会出现**部分成功**（写了 7 个、第 8 个失败）⇒ 结束时必须报「成功 N / 失败 M（含名单）」，
  而不是只弹一句"导出失败"。
- 目录授权目标已存在同名文件时的策略：**默认跳过并计入失败清单**（不覆盖用户文件、不静默改名），
  UI 上把"跳过 N"与"失败 M"分开列。

### 6.2 与侧边文件栏设计稿的实现顺序（仍未定，实现前需确认）

两处动同一块 UI：若先把文件浏览抽成共享组件（`design-side-file-panel.md` 的计划），
选择态应该在**抽取时一次做对**（宿主 VM 持有 `selecting/selectedKeys/onSelectChange`，组件只接收）；
若先在详情页做多选，抽取时要把这套状态搬一次。**两种顺序都能走**，只是搬一次的成本 ≈ 半天。
建议：**若短期内会做侧边栏内联浏览，就先定共享组件边界再做多选；否则直接做多选**（本仓的共享组件
抽取已有先例，搬起来不算大手术）。

## 七、优先级（诚实评估）

相对既有 backlog，本项是**锦上添花**而非填坑：单文件导出 + 分享已经能用，缺的是"一次拿一批"。但它比多数锦上添花更值——因为顺带补上了 **"文件夹根本导不出来"** 这个既存缺口，而且**交互与组件都是现成的**（`ListSelectableItem` + 底部浮动工具条 + 递归删除 API）。
建议排期位置：**与 `design-side-file-panel.md`（侧边栏内联文件管理）一起考虑**——两者都动同一块 UI，选择态的形状应当在共享组件抽取时一次定对；若两者竞争，先做哪个都行，但**先定共享组件边界的那个更省事**。
