# 请求内容预览性能：阶段计时、分词缓存、在飞合并

## 范围

不改变请求组装、BPE 分词算法、插件 WebView 生命周期或精度。不缓存完成的预览结果，避免把时间模板、记忆、文件和插件状态的旧值作为新预览。

## 分阶段诊断

用 `adb logcat -s PromptInspectionPerf` 查看一次实际计算的记录：

- `totalMs`：后台实际组装任务耗时（不含页面绘制及加入已在飞任务前的等待）。
- `memoriesMs`：模型/助手解析和记忆读取。
- `toolsMs`：工具装配。
- `injectionsMs`、`assemblyMs`：来源归因收集与内部消息组装。
- `transformsMs`：完整输入转换链；`transformer_<index>_<class>Ms` 为其中各转换器的嵌套耗时，不能再相加到 total。
- `projectionAndTokenizationMs`：分段归因与文本 token 计数。
- `toolSchemaMs`：工具 schema 序列化和 token 计数。
- `cacheHitsDelta`、`cacheMissesDelta`、`cacheEntries`、`cacheTextBytes`：全局当前 tokenizer 缓存统计；delta 可能包含同期其他请求，tokenizer 重装会归零，不能当严格的单请求归因。

日志仅含固定阶段名、转换器类名、耗时和计数，不包含提示词、工具参数或会话标识。没有承诺具体提速倍数；需要在目标长会话上对比首次与重复打开记录来定位瓶颈。若耗时集中于插件网络/OCR/文件读取，本轮不跳过它们。

## 分词缓存

沿用 TokenizerRegistry 唯一精确计数出口，修复原缓存 access-order get 未同步的问题。所有 LRU 读写、淘汰、统计共用短锁，真正分词在锁外。

- 最多 512 项，缓存 key 文本按 UTF-16 `2 * length` 合计不超过 4 MiB（不是全部对象堆占用）。
- 单文本超过 256 KiB 时不缓存，但仍返回同样的精确结果。
- 每次 tokenizer 安装有独立 cache；release 会失效旧 cache，旧计算不能回灌新实例。
- 没有 tokenizer 时仍返回 null，由既有调用方启发式兜底；启发式结果不混入精确缓存。
- 并发同文本 miss 可以独立计算，避免长分词占用全局锁；预览级重复工作由下述合并器处理。

## 在飞计算合并

ChatService 入口使用 settings/conversation/plugins/MCP 状态的引用快照及 conversationId、labels 作为 key，避免在 Main 深度 hash 大历史。仅引用完全相同的快照会合并；任何状态发布新对象后不加入旧任务。此机制不是对所有外部可变依赖的完整快照隔离。

同 key 的并发调用共用正在执行的任务，完成/失败立即移除，下次重新计算。不同 key 不合并。单个等待者取消不影响其它等待者，最后等待者退出取消共享任务（协作取消，不能回滚插件已经产生的副作用）。VM 也避免 loading 期间重复发起请求，并在切换会话时取消旧任务。

## 实测（Pixel 设备，debug 包，72 条消息 / 297.7K 实际上下文 / 预览估算 370K token）

| 场景 | totalMs | 分词归因 | 占位符转换 |
|---|---|---|---|
| 冷启动后首次打开（优化前） | 17597 / 17152 | projection 12623 / 12453，assembly 3786 / 3641 | 761 / 867 |
| 同进程再次打开（优化前） | 963 / 888 | projection 33 / 18 | 716 / 694 |
| 增加占位符快路径后·冷启动首次 | 17027 | projection 12669，assembly 3810 | **279** |
| 增加占位符快路径后·再次打开 | 426 / 418 | projection 14 / 16 | **238 / 224** |

结论：

1. 首次打开的主要开销是 token 计数（约 12.5s）和组装内部的记忆打分计数（约 3.7s）——两者都是 BPE 冷缓存；进程重启后内存缓存清空，所以每次冷启动都重付一次。
2. 再次打开已由分词缓存覆盖，此时占位符转换占 75%（约 0.7s）：它对每个文本 part 做 20 次全量 `replace` 且无条件复制消息。加上「无花括号直接返回 + 只对命中的 key 求值 + 不复制未变消息」后降到约 0.23s，再次打开从约 0.89s 降到约 0.42s。
3. 冷启动首次打开的 17s 没有改善：那是精确 token 计数本身的代价。要治它需要把计数持久化（按内容哈希落盘）或改为延迟填充，属于独立改动。

新增缓存测试覆盖 LRU、字节边界、并发、release 竞态、词表切换及参考向量冷热结果一致；合并器 9 项测试覆盖共享、隔离、完成后重新计算、失败重试及取消语义；阶段计时测试覆盖嵌套时长不影响阶段 checkpoint。

## 并行计数（A）与进会话预热（C）

- 计数改为 `countTokensInParallel`：按文本轮转分给多个 worker（上限 6），口径不变（仍走同一个 `estimateTokens`），只是把 CPU 分摊到多核。预览先按与分段相同的文本单元并行预取，之后逐段计数变成缓存命中。
- BPE 片段缓存改为每线程独立（原为共享 ConcurrentHashMap）。实测**没有额外加速**——瓶颈不在缓存争用，而在精确计数本身的纯 CPU 成本；改动保留但不计收益。
- 进会话时 `ChatService.prewarmPromptTokenCounts` 在 appScope 后台预热同一批文本单元，同内容签名不重复跑。

| 场景 | 优化前 | 并行计数 + 预热后 |
|---|---|---|
| 冷启动首次打开 | 17.0–17.6s（分词 12.7s） | **10.6–11.1s**（预取 6.4s + 组装 3.6–4.3s） |
| 同进程再次打开 | 0.89s | 0.51s |

实测限制：

1. 6 worker 只拿到约 **2 倍**加速（549K 字符 12.7s → 6.4s）；设备 1+3+4 大小核，并发落在小核上跑不满。
2. 预热只覆盖「原始消息文本」，预览计数的是**转换后**文本（占位符/模板/注入合并都会改内容）——一次预览 158 次命中、126 次未命中，只能省一部分。
3. 剩余大头是串行的组装内计数（记忆打分 3.6–4.3s）与并行预取本身，均未进一步压缩。

## 渐进式渲染（B）

首屏不再等精确计数：`inspectPromptAssembly(onPartial = …)` 先出一版**近似计数**（长文本用字符启发式），分段/目录/正文立即渲染；随后 `refineTokens()` 并行算精确值并覆盖，UI 期间显示「正在精确计数…」。

- `PromptSegment` 新增 `tokensApproximate`（UI 标 ≈ / 提示条）与 `countingText`（重新计数用的原文，避免把「附件占位说明」算进去）。
- 近似只作用于历史/工具输出这类长文本段；工具 schema、记忆计划等本来就算得便宜的段仍是精确值。
- 精确阶段的结果与优化前逐段一致：实测同一会话总 token 仍为 370807。

| 场景 | 优化前 | 现在 |
|---|---|---|
| 冷启动首次打开**首屏可用** | 17.0–17.6s | **4.3s**（组装+分段；近似计数 159ms） |
| 冷启动首次打开**精确值就绪** | 17.0–17.6s | 约 10.7s（首屏后后台补） |
| 同进程再次打开 | 0.89s | 首屏同样即时，精确值 0.5s 内 |

代价：首屏显示的 token 数是估值（已明确标注），滚动到具体段落时精确值可能随后跳变一次。

## D：计数单位与上下文占用对齐

预览的「消息正文」段改为**逐 Text part 计数后相加**（与 `estimateTokenCount` 同口径），不再把多 part 拼成一段再算。这样任何走过上下文统计/预算规划的文本都会命中预览的缓存键；展示正文仍按 `"\n"` 拼接，不受影响。

## C+：预热改为真实组装

`prewarmPromptTokenCounts` 不再只数原始消息，而是在后台跑一遍**真实组装（不含插件 transformer）**并对其分片文本做并行精确计数。这是 C 的有效版本：预热键与预览精确阶段完全一致。

实测（同一会话，进会话后等预热完成再打开）：

| 指标 | 优化前 | C+ 之后 |
|---|---|---|
| 首次打开 totalMs | 17.0–17.6s | **0.52s** |
| 缓存未命中 | 189 | **0** |
| 首屏是否需要近似值 | — | 不需要（精确值当场就绪） |

预热成本转移到了进会话后的后台（约 4.3s 组装 + 计数），且**不运行插件 transformer**，避免预热替用户触发插件副作用。

## 1+2：预热与预览共享同一次组装

- 预热改为接收真实 `PromptInspectionLabels`，并把任务登记到 `warmJobs`；无输入插件时，预热与预览用**同一个 single-flight key** 跑同一份精确计算。
- 预览打开时：兼容则 **join** 预热在飞任务（省掉第二次组装）；不兼容（存在输入插件）则**取消预热**，避免前台/后台抢核——已填充的缓存条目不会因取消丢失。
- VM 在会话加载**之前**先启动预热，让它先占住在飞任务。

实测：同一会话冷启动，进会话后立刻打开预览，全程只出现**一条**组装日志（此前预热与预览各跑一遍、预热还拖慢了前台的并行计数，预取从 6.4s 涨到 8.3s）。首屏内容仍在约 4s 量级，精确值随后补齐。

未做：以设备日志逐条确认「这次是 join 还是 join 失败后走渐进式」——两条路径产生的日志形状相同，需要额外打点才能区分。

## 组装内部：记忆 L2 计费并行化

计时打点定位：`assemblyMs` 的 3.6s 中 **L2 全文层独占 3.48s**（`mem_l2`），其余阶段全部 ≤ 5ms；L2 内部打分仅 113ms，**3.48s 全是逐条「试渲染 + 精确计数」**。

改法：把「每条记忆多贵」这部分（彼此独立）抽成 `precomputeMemoryEntryCosts()`，用 `countTokensInParallel` 先行算热，计划阶段直接查表；选中与否仍是原来的串行贪心，顺序与结果字节不变。

实测：

| 指标 | 改前 | 改后 |
|---|---|---|
| `mem_l2Ms` | 3481ms | **0ms** |
| 并行预算 `memoryCostsMs` | — | 1088ms |
| 整次预览 `totalMs` | 12.5s | **10.4s** |

（第一次尝试「组装前预取历史文本」无效，因为组装原来根本不数历史消息——已回退。）

## ③ 首屏骨架：先给条数，再给分段

进入预览页立刻显示「已加载 N 条消息，正在统计分段…」——`N` 来自会话快照（`promptInspectMessageCount`，不触发任何组装/分词），随后被真实分段结果替换。这是 B 渐进式渲染里最早的一帧。

被取消的 ①：原计划「跳过必然被截断的内容」在这条链路上**没有可省**——预览的分段与计数都发生在 `buildSendWindowMessages` 截断之后，549K 字符全部属于会真实发送的内容。

## 持久化计数缓存（跨进程）

`TokenCountDiskCache`：把精确 BPE 结果按**文本哈希**（SHA-256 前 8 字节）落到 `files/token_counts.v1.bin`，冷启动直接复用。

- 只缓存**真 tokenizer** 的结果（启发式兜底值绝不落盘，避免把错值"固化"成永久命中）；
- 文件头带**词表版本**，词表变了整份丢弃；
- 上限 2 万条、节流 3s 落盘、原子替换写；
- 键是哈希不存原文：1.5MB 文本 → 12 字节/条。

实测（同一会话，连续三次冷启动）：

| 冷启动 | tokenPrefetch | totalMs |
|---|---|---|
| 第 1 次（空缓存） | 8448ms | 11.1s |
| 第 2 次 | 1076ms | 8.2s |
| 第 3 次 | **26ms** | **3.9s** |

第三次仍有 `projectionAndTokenizationMs≈2.6s`。此前把它归因于 transformer 时间注入，但当时没有易变区段命中数据，不能据此确定原因。后续检查还发现：并行预取按整条消息拼接文本，而投影按每个 Text part 分别计数，二者缓存键不一致；本轮已将预取单位同步为逐 Text part。时间提醒使用消息自身时间，模板的普通消息日期也来自消息自身，不能笼统视为每轮变化。

## 易变区段增量计数（B 路线）

- `MessageTransformer.volatileSpans` 可选声明输出文本的 UTF-16 区间；按每条消息 Text parts 以单个换行拼接后的坐标计算，不含附件说明与工具输出。
- `transformsCollectingVolatileSpans` 按消息 id 保留/迁移标注：包装会偏移，删除会丢弃，被改写且无法安全定位的标注丢弃。越界、空区间剔除。普通发送链不收集标注，避免额外成本。
- Placeholder 标注替换区间；Template 标注正文之外的包装，无法识别单一正文时保守标记改写区。多处替换可合为大区间（牺牲命中率，不牺牲正确性）。
- JS manifest 可选 `volatilePatterns: ["正则表达式"]`，按 JVM Regex 校验；桥接只匹配输出，不再次执行脚本。不声明时保持原行为。
- **16 字符是最小上下文，不是精度假设**：易变窗口扩展到完整 BPE 预分词匹配；空白 lookahead 依赖一并保留，稳定块复用现有磁盘/内存计数，变化块直接 BPE。不是 `count(规范化文本)+差值`，不把人为标记当真实 token，也不固化近似值。
- 随机与边界单测验证和同一 tokenizer 的整段计数完全相等；无安全切分时退回整段。

设备复测（保留已有持久缓存，重启进程两次）：总耗时 3.009s / 2.544s，预取 1.709s / 1.281s，投影 4ms / 5ms。**两次 annotatedTexts=0，不能把改善归功于易变区段优化**；目前这段会话未触发标注，改善含预取口径修正及缓存状态差异。带动态日期的真实词表单测单独覆盖稳定主体复用与精确计数。

这里的“检查点式复用”只复用可证明边界安全的稳定文本块，不改请求内容，不插入模型可见检查点；也不承诺与服务端 tokenizer、聊天协议开销逐 token 一致，只保持与本地整段 BPE 计数一致。

## 预分词正则换成手写扫描器（真正的瓶颈）

前面的归因（"分词慢""BPE 合并慢""debug 包解释执行慢"）都被后续测量推翻。用 128KB 构造会话（正文完全相同、只有一行 `{{model_name}}`）逐层加埋点：

- `splitMs=4392 / countMs=8`：切分 4.4 秒、计数 8 毫秒 ⇒ **成本全在预分词扫描**，稳定块缓存本身是命中的。
- 设备标定（12.8 万字符）：普通 char 循环 27ms，`PRE_TOKEN_PATTERN` 扫描 3360ms（23819 个匹配）。
- **release 包（R8、非 debuggable）同一扫描 2386ms，debug 2572ms——只差 1.1 倍**，所以不是构建类型的问题。
- 同一设备对比：cl100k 正式正则 2572ms；`[^\s]+|\s+` 这种极简正则 4418ms（更慢）；**手写字符遍历 26ms**。
- 桌面 JVM 同一段扫描 2–3ms。

⇒ 这台设备上 `java.util.regex` 的 `Matcher` 本身极慢，与模式复杂度和构建类型都无关。token 计数是所有预算判定的公共底座，这一层慢会拖慢预览、上下文占用条、自动压缩、记忆注入。

**改动**：`ByteLevelBpe.nextPieceEnd` 手写实现 cl100k 的 7 条预分词规则（缩写 / 可选前缀+字母串 / 1–3 位数字 / 空格+符号串+换行 / 空白+换行 / 空白不后接非空白 / 空白兜底），按**码点**遍历（补充平面字符与正则一致）；`count` / `encode` / 易变区段切分全部改走它。`\p{L}` / `\p{N}` / `\s` 的语义逐项对应 Java 正则（`\p{N}` 是 Number 大类、`\s` 用本仓展开的 Unicode 空白集、``/`
` 单列）。

**正确性**：新增 `ByteLevelBpePreTokenParityTest`，把片段边界与正则逐段对拍——30+ 条固定边界向量 + 6 万条随机语料（含 CJK、韩文、假名、阿拉伯数字、罗马数字、上标、emoji ZWJ 序列、组合符、各类空白），另有 `count == encode.size` 随机校验；原 `ByteLevelBpeVolatileSpansTest`（500 组随机）继续通过。

**设备实测**（清空持久缓存后冷启，128KB 构造会话）：

| 阶段 | 之前 | 之后 |
|---|---|---|
| 冷启组装 | 3787–6906ms | **234ms** |
| 同进程二次预览（精确计数） | 4359ms | **1ms** |
| 重启后再次打开 | 4359ms | 56ms（整段缓存命中） |

配套的另外两处改动：易变区段切分改为单次流式遍历（不再物化两万多个 `MatchResult`，切分 4392ms→3551ms）；切分得到的精确总数写回持久缓存并加整段命中快路径。

## 附带修复：`{{cur_datetime}}` 不是有效占位符

内置提示词里写着 `Time: {{cur_datetime}}`，但占位符表只有 `cur_date`，于是这段**原样发给模型**。已补 `cur_datetime`（`LocalDateTime` + 本地化日期时间格式）与三语文案（en / zh / zh-rTW）。
