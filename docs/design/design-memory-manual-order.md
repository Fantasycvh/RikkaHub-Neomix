# 记忆卡片拖拽排序（仅显示顺序）

> 状态（2026-10-17）：**仅设计稿，未落地、未实测**。
> 用户拍板的范围：**A 方案 —— 只影响显示（装饰性）**；`sort_key` 空档**暂不压缩**；
> 恢复的记忆**排到末尾可接受**，但要像对话/预览页那样提供**侧边回顶/回底**。
>
> 相关：`design-memory-recycle-bin.md`（恢复置底的语义与本稿一致）、
> `design-memory-scoring.md`（importance / 预算 / 锚点 —— 本稿**不碰**）、
> `design-conversation-manual-order.md`（同类拖拽排序的先例与教训）。

## 1. 范围（先说清「不影响什么」）

**只改显示顺序。** 明确**不**影响：

| 机制 | 现状 | 本稿是否改动 |
|---|---|---|
| 注入选取 | `buildMemoryPrompt` 取**最新 60 条**（`sortedByDescending { it.id }.take(60)`） | **不改** |
| 注入优先级 | importance 分数 + 8K token 预算 + L1 锚点 | **不改** |
| 淘汰 | 超 200 条按**分数**淘汰（与顺序无关） | **不改** |

⇒ 这是**装饰性排序**。做它的理由是可读性（把同类记忆聚在一起），**不是**"让模型优先看到"。
若哪天要后者，那是锚点/优先级的活，不是本稿。

## 2. 数据模型

- `MemoryEntity` 新增 `sort_key: Long`（**不加唯一约束** —— 空档与重复都不压缩）
- **迁移**：存量行按 `id` 回填 `sort_key = id`（等价于"保持现状"）
- `AssistantMemory.sortKey` 从 `= id` 改为真实字段（`MemoryRepository.kt:52`）
- 新增/编辑不改变 `sort_key`；**插入**时赋 `sort_key = (max(sort_key) ?: 0) + 1`

## 3. 消费点

| 位置 | 改动 |
|---|---|
| DAO 四处显式 `ORDER BY id ASC` | 改 `ORDER BY sort_key ASC`（**仅内存列表相关的展示查询**） |
| `buildMemoryPrompt` 的 `sortedByDescending { it.id }` | **不动**（它选的是"最新 N 条"，与显示顺序无关） |
| `enforceMaxCount` | **不动** |
| 整理器的合并/删除 | **不动顺序**：幸存者保留原 `sort_key`，新记录追加 |

⚠️ **一处必须核对**：2026-09-14 修 `take(60)` 缺陷时给 `MemoryDAO` **四处**补了显式 `ORDER BY id ASC`
（为保持展示顺序）。这四处里**哪些是"展示"、哪些是"注入取数"**必须逐处确认再改 ——
把注入取数也改成 `sort_key` 会**静默改变模型看到的记忆集合**，那是本稿明确不想要的。

## 4. 交互

**拖拽**：复用会话列表那套（`design-conversation-manual-order.md` 的实现）。

**侧边回顶/回底**：**已有现成组件** `ui/components/ui/ScrollJumperBar.kt`（165 行，
`BoxScope.ScrollJumperBar`），提供「进度文字 + 回顶 + 上一项 + 下一项（+ 回底）」，
已经被 `ChatList.kt:641` 与 `PromptInspectPage.kt:209` 使用 —— 就是用户说的「对话/预览」那两处。
记忆页直接放一个即可，**不需要新写**。

拖拽落盘时机：**松手即写**（一次拖拽一行 UPDATE）。记忆最多 200 条，不需要批量提交。

## 5. 边界语义

| 场景 | 行为 |
|---|---|
| **回收站恢复** | 重新插入 ⇒ 新 id、**`sort_key = max+1`** ⇒ **置底**（与回收站设计稿 §5.1 一致） |
| **整理器新增/合并** | 新增置底；合并保留幸存者 `sort_key` |
| **删除** | **不压缩空档**（用户明确） |
| **批量操作**（如整理批量删除） | 剩余项 `sort_key` 不变 |
| **排序后新增** | 总是追加到末尾，不插入中间 |

## 6. 先例的教训（会话列表 v1.0.23 批 1–3b）

真机修过三个 bug，**其中两个同样会犯**：

- ❌ **分页崩溃** —— 记忆最多 200 条、**没有分页** ⇒ 这类不适用
- ⚠️ **落点差一位** —— 会犯：拖拽的"插入点"与"目标索引"差一，必须用**明确的插入语义**（插到目标项之前/之后）而不是"交换"
- ⚠️ **空拖写库** —— 会犯：拖拽距离为 0（或落回原位）时**不得写库**，否则每次误触都产生一次 UPDATE + 一次 UI 重排

这两条要在实现时**写成守卫/单测**，不靠"注意一下"。

## 7. 明确不做

- **不影响注入顺序**（见 §1）
- **不压缩 `sort_key` 空档**（用户明确：暂不）
- **不做恢复保序**（恢复必置底，可接受）
- **不引入"分组/标签"** —— 排序只是把已有的东西摆整齐，不是新的组织维度

## 8. 未验证

- 四处 DAO `ORDER BY` 里哪些属于展示、哪些属于注入取数，**未逐处核对**（§3 的 ⚠️）。
- `ScrollJumperBar` 在**短列表**（< 一屏）下的表现未确认 —— 记忆少时它可能不该出现（需要 `show` 判定）。
- 触屏拖拽在 200 条列表上的可用性**未实测**（用户是否真的会用它管理这么多，本身也存疑）。
