## 0. 一句话

现状压缩是「逐条截断 → 分块并行独立摘要 → 拼接」；本文把它改成「**滚动携带的分块摘要**（第一步，直接落地）+ **锚点精炼遍**（第二步，快速模型 + 回声护栏）+ **语义分段**（第三步，暂缓）」，并明确与上下文净化的分工——**关联在判据库，不耦合在流程**。

## 1. 现状与损失点

`compressToCheckpoint`（`ChatService.kt:2214-2319`）的摘要流水线：

```
待压缩消息（可能数百条）
  → summaryAsText(maxLength = 2000) 逐条转文本     ← 损失 ①
  → splitIntoChunks(256 条/块) 并行独立摘要        ← 损失 ②
  → joinToString("\n\n") 拼接 = 最终摘要            ← 损失 ③
```

| # | 损失点 | 位置 | 说明 |
|---|---|---|---|
| ① | **单条截断**：每条消息只取前 2000 字符，超出部分任何后续步骤都救不回 | `ai/.../ui/Message.kt:201-208` | `text.take(maxLength) + "..."` |
| ② | **块间失忆**：块并行、彼此独立，跨块指代断裂（人名/任务/文件在第 2 块首现、第 5 块再提时模型不知它是谁） | `ChatService.kt:2284-2288`、`CompressionPlanner.kt:91-100` | 且 prior 检查点被**每个 chunk 重复注入**（`ChatService.kt:2252-2257`），N 块 = N 份「请与 prior 合并」的半成品再拼接 |
| ③ | **无整体校验**：块间矛盾、重复、漏关键事实直接入档；检查点是**永久**载体 | `ChatService.kt:2288`、`:2309-2310` | 拼接 ≠ 合并 |

并行设计的初衷是**速度**；代价是精度。本文的三步都在这个权衡里做文章。

### 1.1 摘要输入只取 Text part（决定与净化的耦合面）

`summaryAsText` 的 `when (part)` 里**只有 `UIMessagePart.Text` 产出文本**，`Reasoning` / `Tool`（含输出）全部为空串：

- **推理残留不进压缩输入**（净化稿的主目标物在压缩这里天然被丢弃）；
- 工具轮（`[Text, Tool, Text]` 形状）进摘要的只有两段文本，调用与结果本身不进。

⇒ 压缩与净化的真实重叠面只有 **Text part 的字面重复**（§6.3），比直觉小得多。

### 1.2 核验补充的四条现状事实（2026-10-24，并行会话确认）

| # | 事实 | 锚点 | 对本文的影响 |
|---|---|---|---|
| A | **口径分歧不止影响触发，还影响保留预算**：`estimateCompressionPlan` 用本地 `estimateTokenCount`（只算 Text+Tool）从尾部定保留窗口，触发用的真实 usage 计入 reasoning ⇒ 回传推理的 OpenAI 兼容会话按 0.4 保留比切完后，保留窗口**实际**占用高于名义预算——压完仍可能超标 | `CompressionPlanner.kt:78`、`ContextLength.kt:58-92` | 补进 §6.1；**不在压缩侧修**——往 `estimateTokenCount` 加 Reasoning 会对 Claude/Gemini（编码层丢推理）反向高估，正确估算依赖 provider 家族 |

## 2. 方案总览

| 步骤 | 解决什么 | 成本 | 改动面 | 建议 |
|---|---|---|---|---|
| 1. 滚动摘要 | ②块间失忆 + prior 重复注入；顺带 ①（超长单条独占 chunk）与 D（分块带 token 预算） | 并行→串行（块数通常 1~3，延迟增幅可控） | `compressChunk`/分块/合并约 40-60 行 + prompt 一段 + 一行统计日志 | **先行落地** |
| 2. 精炼遍 | ③无校验 + ①的兜底 | +1 次 LLM 请求（输入仅摘要+锚点，几百 token，快速模型） | 新 resolver 小链 + 新函数 + 一次调用（fail-open） | 第 1 步观察一版后上 |
| 3. 语义分段 | 让块边界对齐话题边界 | 纯本地，零请求 | 新分段函数替换 `splitIntoChunks` 调用点 | 暂缓（长会话才明显） |

三步**正交可独立落地**；第 2 步依赖第 1 步的锚点产出（顺带），第 3 步谁都不依赖。

## 3. 第 1 步：滚动摘要（rolling map-reduce）

### 3.1 算法

```
carry = prior 检查点（可为空）
for chunk in chunks:                 // 串行
    Si = LLM(压缩提示词 + chunk + carry)   // Si 是「合并摘要」，不是增量
    carry = Si
最终 = carry (= Sn)
```

- prior 检查点只作为**初始 carry** 注入一次（消除现状的每块重复注入）；
- carry 走现有 `{additional_context}` 占位符（`ChatService.kt:2268-2273` 的 `applyPlaceholders` 不用改），措辞加一段「PRIOR SUMMARY（与本块合并为单一摘要，不要分段拼接）」；
- 用户 `additionalPrompt`（手动压缩的附加指令）每块保留注入（它是约束不是内容，重复无害）。

### 3.2 超长单条与分块预算（针对 ① 与事实 D；收敛自 Q5）

**按 token 切，字符帽只做兜底**：

- **单条帽**：`min(32K token, 压缩模型 effectiveContextLength / 2)`。64K 字符对中文正文 ≈ 4~6 万 token，加 carry 和提示词就顶到压缩模型窗口——字符帽的「静态值」不可靠。token 估算用 `estimateTokens`（全仓唯一出口，`ContextLength.kt:127`）；超帽仍截断并标记 `[truncated]`；
- **超长单条独占 chunk**：转文本阶段检测单条超阈值（约 8K 字符）→ 该条不截断、独占一块（受上述 token 帽约束）；
- **`splitIntoChunks` 增加 `maxTokens` 参数按估算切**，256 条只留作条数上限——顺带修掉事实 D 的潜在超窗。这是 §3.2 的自然强化而不是新功能。

### 3.3 失败语义与观测（收敛自 Q1）

**fail-fast 落地**（第 N 块失败丢弃已生成的 S1..S(N-1)，整体重试；压缩落库前失败不产生半检查点，幂等安全），同时把失败分类说清即闭环：

| 失败类别 | 处置 |
|---|---|
| 瞬时网络/限流错 | 重试整跑（唯一断点续跑有价值的类别，块数多时才值得——先拿数据） |
| 块超窗 | 被 §3.2 的 token 帽**预防**，不再出现 |
| 退化内容 | **不算失败**，走 §4.2 降级路径 |

**观测从第一版就埋**：每次压缩记录块数与每块 token 数（一行 `Log.i`）。这个数据**不用等滚动版实现**——现状并行实现里就可以先埋，Q1 需要的分布数据现在开始攒，滚动版的延迟决策（值不值得为它做断点续跑）将来直接查表。

### 3.4 延迟账

- `COMPRESS_MAX_MESSAGES_PER_CHUNK = 256` 意味着**多数会话只有 1 块**——1 块时滚动 = 现状，零回归；
- 2~3 块的长会话串行化后总时长 ≈ 各块之和（现状 ≈ 最大块）；自动压缩在后台触发、不打断发送，用户可感影响限于手动压缩的等待。

### 3.5 失败阶梯（压缩档 C0–C4）与覆盖率闸（revision 3 新增，C3→C2→C4 已落地）

来源：NMoi-Agent P4.3 失败阶梯（`docs/compression.md`，**设计未实现**——抄形状与判据，勿照抄「已实现」印象）。
命名用 **C 档**避开本仓记忆分层 L0–L3（`design-memory-injection-tiering.md`）的冲突。

| 档 | 做什么 | 状态 |
|---|---|---|
| C0 | 滚动摘要 + 精炼遍（本稿 §3 + §4） | 未落地（本稿主线） |
| C1 | 仅滚动摘要（精炼失败时降到此档） | 未落地 |
| C2 | **单步整体**：全部待压内容一次调用 | **已落地**（本轮） |
| C3 | 分块并行 + 拼接（现状流水线） | **已落地**（原路径） |
| C4 | **截断 + incomplete 声明**（确定性，无 LLM，必然成功） | **已落地**（本轮） |

四条原则（NMoi 同款）：

1. **压缩不可重入**：阶梯执行期间不再触发新的压缩；
2. **退档只许一层**：C3 失败退 C2，C2 失败退 C4——不允许可重入的多层分段（防最坏 4×16 次调用烧穿额度）；
3. **C4 诚实声明**：摘要正文带 `[compression incomplete: …]`，界面与下游都知道「这轮压缩没通过校验，是原文截断」——对齐本仓预览页「绝不静默降级」的哲学；降档落库时打 `Log.w`；
4. **同一次压缩冻结模型**：各档用同一模型（NMoi D76），不在档间换模型导致风格漂移。

**覆盖率闸（每档产出后过闸，代码侧、不问模型）**：从原文提取**硬事实**（文件路径 / 版本号串 / ≥3 位数字与百分比，各取并去重、上限 64 条），摘要必须**逐字命中** ≥80%；事实 < 4 条豁免（纯散文不误伤）。这不是新要求——默认提示词 Rules 已要求「Preserve exact file paths…numeric values」，闸是**执行确认**：不达标就是失败，不「大概齐」（NMoi 同款原则）。阈值 0.8 与护栏/净化的 containment 同一档位量级，宁松勿严——误杀的代价是多付一次调用，漏杀的代价是丢事实，方向不对称。

**落地状态（2026-10-26，本轮）**：`CompressionLadder.kt`（覆盖率闸纯函数 + 阶梯编排，summarizer 以 suspend lambda 注入 ⇒ JVM 单测）+ `compressToCheckpoint` 接线（C3→C2→C4，C2 在原文 > 60K 字符时跳过——单步请求自身会超窗）。C0/C1 待滚动摘要落地后按本阶梯接入；真机观察随下个版本进行（本轮仅单测验证）。

**第一人称规则（NMoi D147，已进默认提示词）**：实测同一份内容，摘要写第三人称（「用户与助手约好…」）高置信率 22–38%，第一人称记忆（「我记得我说过…」）62%，文件口吻从 20–22% 降到 0%——**人称比条数重要**。默认 `DEFAULT_COMPRESS_PROMPT` Rules 已加一条 first-person 要求；C0/C1 的滚动/精炼提示词落地时同款跟进。

**验收指标（借 NMoi D143/D145，替代「人工评估连贯性」）**：压缩质量改动（提示词/阶梯/滚动）统一看三个可算指标——**要点命中 ≥ 0.9**（锚点清单被摘要覆盖的比例）、**思考长度膨胀 ≤ 1.5×**（压缩前后模型对同一问题的推理长度比）、**文件口吻率 ≤ 5%**（摘要读起来像「描述一份文件」而非「我记得」的比例，抽样人工判）。§8 的真机评估项据此升级。

## 4. 第 2 步：精炼遍（refine pass）

### 4.1 模型与护栏（收敛自 Q2；含 §1.2-B 勘误）

~~「快速模型 + 同款回退语义已有基建」~~ → **勘误**：`resolveCompressionModel` 链不含 fastModelId（事实 B），需**新写**一条小链：

```
resolveRefineModel = fastModelId → 压缩模型(resolveCompressionModel 的结果) → 对话模型
```

（照 MemoryConsolidator 链的形状写，`MemoryConsolidator.kt:106` 同款 `?:` 链即可。）

三道护栏让精炼遍对弱模型免疫：

1. **回声指令**：提示词写明「未发现缺陷时**原样返回**摘要」——弱模型最坏情况变成回声，而不是改坏好摘要；
2. **长度健全性检查**（本地）：精炼输出空白或比 Sn 短得多（< 50%）→ 丢弃精炼结果、保留 Sn；
3. **fail-open**：精炼遍调用失败（网络/限流）→ 保留 Sn 继续落库。可选增强步骤的失败不拖垮整个压缩。

### 4.2 锚点机制与 containment 自检

第 1 步的压缩提示词**顺带要求**在摘要末尾输出锚点清单（格式见 §4.3）。精炼遍输入 = `Sn + 锚点清单`，指令：「核对摘要是否覆盖每条锚点、有无自相矛盾或重复段落，输出修订版」。覆盖不了的锚点 → 「列出缺失项 + 从摘要可见信息尽量补写，仍不可得则标注 (lost)」——不假装能找回。

**锚点核对之外，补一个代码侧因子（revision 3，借 NMoi 三因子置信度）**：模型自评不可信（0–1 自评无法校准），精炼遍的核对拆三层——**硬事实字符串命中**（代码：§3.5 覆盖率闸同款提取，权重设想 0.45）、**锚点覆盖**（§4.3 清单，0.35）、**模型核对结论**（0.20）。代码侧两层先跑，模型核对只处理代码判不了的语义遗漏；阈值只拉低不拉高（压得保守最多是长，压得激进就是丢事实）。

**廉价保险（滚动污染的输出侧检查）**：每生成一个 `Si`，本地跑一次字面重复判定；命中则该块降级——**丢弃 Si、该块原文跳过压缩（最终摘要标注 `[skipped: degenerate]`）**，carry 保持上一值继续。净化落地后可升级为输入侧预清理（Text part 预剥离再进摘要），共用判据库、不共用流程。

**阈值不借用护栏标定值，重新标定**（收敛自 Q3）：

- **比对对象不同**：这里测的是「Si 自身内部重复」（尾部对前部），护栏测的是「当前推理对上一段推理」；护栏那套 4000 字符 shingle 窗口的参数在 ~2000 token 的摘要上不适用；
- **分离度更有利**：合法摘要是浓缩散文，内部 containment 天然低；退化摘要（回声复读）接近 1——比护栏场景（表格 0.72 vs 退化 0.92）分离更宽；
- **方向偏严**：误杀（跳块 = 该块内容整体不进摘要）是最重的动作，比漏杀（脏摘要进档）更贵，阈值宁高勿低；
- **照净化 P0 模式：先记录后定**——第一版只记录每次压缩的 Si containment 值，阈值从观测分布里定；定下来之前用保守高值 **0.95** 挂降级路径。

### 4.3 锚点格式：固定 schema（收敛自 Q6）

「限制表达」的顾虑放错了对象——锚点是摘要的**附录**不是摘要本身，定死格式不约束摘要散文：

```
<anchors>
- [fact] 用户在使用 RikkaHub fork，包名 app.androidrik
- [decision] 保留比维持 0.4，不为编码场景调低
- [task] 待办：滚动摘要落地后观察一版再上精炼遍
- [value] 阈值暂定 0.95
- [file] docs/design/in-progress/design-multi-pass-compression.md
- [name] 提交者 re-ovo / 并行会话
</anchors>
```

- 类型限 **{fact, decision, task, value, file, name}** 六种；条数封顶 **20 行**（顺带给精炼遍输入定了上界）；
- **入档前剥离**：固定围栏块是精确切割，自由文本的剥离是模糊匹配——这也是必须定死格式的实操理由。锚点清单只是中间产物，检查点仍只存摘要正文。

## 5. 第 3 步：语义分段（暂缓）

按话题边界切块：信号候选 = 相邻消息时间间隔突增 / 会话内标题变化 / 关键词分布突变。纯本地规则，零请求。暂缓理由：滚动携带已大幅缓解「块边界切断话题」的代价（后块能看到前块摘要），分段的边际收益集中在话题跨度极大的会话，先拿数据说话。

## 6. 与上下文净化的关联（跨设计接口）

> 结论：**关联在判据库，不耦合在流程**。净化侧的对应记录由净化稿自理（本文只管压缩侧）。

### 6.1 触发与预算的口径耦合（含事实 A）

`estimateWindowTokens`（`ContextLength.kt:58-73`）**优先取真实 `promptTokens`**，本地兜底才用 `estimateTokenCount`。两路径对推理残留的口径**不一致**：

| 路径 | 残留计不计 | 后果 |
|---|---|---|
| 真实 usage（触发用，优先） | **计**（OpenAI 兼容默认回传 `reasoning_content`，provider 计入 promptTokens） | 严重退化抬高占用读数 → **提前触发**不可逆检查点 |
| 本地估算（保留预算用，`estimateCompressionPlan`） | **不计**（`ContextLength.kt:82-92` 只算 Text+Tool） | 切完的保留窗口**实际**占用高于名义预算——**压完仍可能超标**（事实 A） |

**处置：两边都不动，等净化对齐**——往估算里加 Reasoning 会对 Claude/Gemini（编码层丢推理）反向高估，正确口径依赖 provider 家族，单独修任何一边都会修错方向。

**对齐是「部分」的，要写准**（净化稿记账用）：净化落地的效果是发送内容与估算口径**部分**对齐——对齐的只有退化残留那部分；合法推理的差值仍在（provider 相关，Claude/Gemini 发送侧本来就丢）。不能写成「分歧消失」。

### 6.2 接力关系：压缩边界是残留的「终点站」

- 净化管**在途**：上一轮窗口（`u_prev, u_last`），治理「自己教自己」；
- 压缩管**终点**：残留随轮次越过检查点边界后被 Text-only 摘要**永久丢弃**（§1.1）；
- 净化窗口够不着边界前的老残留——那部分由压缩天然兜底。两层防御**接力**，无冲突需要协调；净化稿「压缩管预算，净化管质量」在代码层即此形状。
  （2026-10-24 跟进：净化稿 revision 5 已把作用域反转为「发送窗口内全部已完成轮次」，本句前半失效——净化窗口现直达检查点边界，老残留同样被清；接力关系本身不变，见净化稿 §15.1。）

### 6.3 唯一真实重叠：Text part 字面重复（含事实 C）

退化泄漏进正文时会以「前 2000 字」进摘要输入，滚动化后还会**向后传播**（§4.2 保险的动机）。事实 C 确认：**Text 重复今天无任何消费者**（护栏读 `reasoningText()`，净化 C 系规则只碰 Reasoning/Tool part）——判据库的第三个消费者（压缩输入侧预清理）目前是唯一候选，两边都不覆盖谁。

### 6.4 判据库：一库三消费者

```
字面重复判据（containment / minimalPeriod / distinctChars，护栏已 internal）
  ├─ 护栏：调用内/边界停止
  ├─ 净化：发送副本 part 级剥离（净化稿 §4.2 计划同源）
  └─ 压缩（本文）：§4.2 输出自检（阈值独立标定，§4.2）→ 将来输入预清理
```
