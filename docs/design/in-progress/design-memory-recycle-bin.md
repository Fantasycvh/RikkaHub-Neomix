# 记忆回收站（软删除）

> 状态（2026-10-17）：**仅设计稿，未落地、未实测**。
> 起因：`memory_tool` 的 `delete` 至今**不可逆**，而 2026-10-16 刚让「记忆整理」可以**批量提出删除建议**
> —— 风险面被显著放大（一次误采纳就是多条永久丢失）。
>
> 相关：`design-memory-scoring.md` §七（原始回收站设想与两个坑）、
> `design-memory-retrieval-and-consolidation.md`（整理建议落库与按批语义）。

## 1. 要解决什么

`delete` 不可逆。在当前链路里这条风险被两件事放大：

1. **整理会批量提删除建议**（2026-10-16 落地），用户可能一次采纳多条；
2. **删除是"静默成功"** —— 没有回收站，就没有"我删错了"的补救路径。

目标：让删除**可逆**，且**不改变现有删除语义的速度/成本**（不弹确认框、不加二次确认）。

## 2. 为什么不用「加一个 `deleted_at` 列」

`design-memory-scoring.md` §七 已经记过两个坑，两个坑的**根源都是「被删的行还留在 `memory` 表里」**：

| 坑 | 根源 | 影响面 |
|---|---|---|
| **软删算不算 200 条配额** | `getMemoriesOfAssistant` 被**注入 / UI / 幂等检查**三处共用 | 改语义波及全部三处 |
| **幂等检查会「复活」被删记忆** | 同内容复用逻辑会命中回收站里的条目 | 删了又"自己回来" |

**关键洞察**：把删除的行**搬出 `memory` 表**，这两个坑**同时消失** —— 行真没了，配额不用改语义，幂等检查也查不到。
这比「加列 + 逐个改三处调用点」干净得多。

## 3. 为什么不用「临时文件」

「把删除的记忆写入临时文件、过期后清理」这个方向**核心判断是对的**（同样是"搬走"），
但落到文件会引入四个新问题：

1. **原子性**：DB 删除与写文件不是一件事，进程在两步之间被杀 ⇒ **记忆丢了、回收站里也没有**。
   只能靠「**先写文件、再删行**」的写前日志把损失方向反过来（变成"可能多一条"而非"少一条"）。
2. **损坏与版本**：手写 JSON 要自己管格式版本、半截写入、并发写。
3. **不参与备份/导出**：DB 备份带不走它 ⇒ 换机后回收站里的内容**静默消失**。
4. **UI 要另写一套读写**：记忆页展示回收站时得绕开 Room 直接读文件。

⇒ **同样收益、更少失败模式的做法是「一张独立的表」。**

## 4. 方案：`memory_trash` 独立表

**无外键**（同 `MemoryProposalEntity` 的模式，2026-10-16 新建表时已确立）。

| 字段 | 说明 |
|---|---|
| `id` | 自增主键 |
| `original_id` | 原 `memory.id`（**仅作诊断/展示**，恢复时不复用 —— 见 §5.1） |
| `assistant_id` / `content` / `importance` / `is_anchor` / 原 `created_at`/`updated_at` | 原行快照 |
| `deleted_at` | 删除时刻 |
| `expires_at` | 过期时刻（默认 30 天，可配） |
| `origin` | `user` / `consolidation`（区分"用户主动删"与"整理建议删"，便于以后做统计） |

**为什么它比文件方案好**：
- 事务原子（**入站 + 删除原行在同一事务**）
- 可查询、可进备份、UI 直接读
- 一次迁移（本仓这轮已做过 38→39、39→40，流程是熟的）

## 5. 必须先定的三个语义

### 5.1 恢复会换 id（接受它）

`AssistantMemory.sortKey = id`（自增行 id，`MemoryRepository.kt:52`），**恢复等于重新插入** ⇒
**新 id、排到最后**。

- 若"恢复后置底"可接受 ⇒ 最简单，**本设计按此做**
- 若必须保序 ⇒ 得另加排序列 —— 那是更大的改动，**不在本设计范围**

⇒ UI 上要**明确写出**"恢复后置底"，避免用户困惑。

### 5.2 过期清理的时机与上限

- **时机**：App 启动时扫一次 + 打开记忆页时扫一次。**不做前台定时器**（移动端不划算）。
- **上限**：除时间外**再加条数上限**（建议 200），避免一次全量整理把站撑爆。
- **天数**：默认 30 天，可配置。

### 5.3 哪些路径走回收站、哪些必须绕开

| 路径 | 处置 |
|---|---|
| `memory_tool` 的 `delete` | **走** |
| 整理建议的 `delete`（含批量采纳） | **走** |
| `AssistantVM.kt:54` 删助手时的级联硬删 | **绕开**（故意：助手都没了，回收站没有归属；原设计已写明） |

**一个容易漏的点**：整理建议的 `delete` 可能与 `edit` **同批**。2026-10-16 已定「同批有未勾选成员则跳过 `delete`」
（`MemoryProposalApplyResult.blocked`）—— 回收站**不改变那条规则**，只是在它落下去之后多存一份快照。

## 6. 落地顺序

| # | 步骤 | 说明 |
|---|---|---|
| 1 | `memory_trash` 表 + 迁移 + 测试 | 无外键；DTO/DAO 照 `MemoryProposalEntity` 模式 |
| 2 | 删除路径写入（**同事务**） | 先落站、再删原行；整理建议删除也走这条路 |
| 3 | 过期 sweep（启动 + 打开记忆页） | 时间 + 条数双上限 |
| 4 | 记忆页「回收站」UI | 列表 / 恢复（置底）/ 清空 / 显示剩余天数 |
| 5 | 整理建议删除纳入 | 与 2 共用同一入口 |

**阶段 1–3 就能兜住风险**（删除可逆），阶段 4 才是"用户可见的回收站"。

## 7. 明确不做 / 边界

- **不做**「恢复后保序」（需要排序列，另立项）。
- **不做**「回收站计入 200 条配额」—— 行不在 `memory` 表里，天然不计。
- **不做**「删助手时保留回收站」—— 级联硬删是故意的。
- **不做**「回收站参与记忆注入/整理」—— 它在模型视野之外，只在 UI 可见。

## 8. 未验证

- 「恢复后置底」的用户接受度**未验证**（这是本设计最可能被推翻的假设）。
- 30 天 / 200 条两个默认值**未实测**，只是防止无界的保守取值。
