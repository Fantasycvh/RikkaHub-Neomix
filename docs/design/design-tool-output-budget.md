# 工具输出预算与降级（设计稿）

> 状态（2026-10-17）：**仅设计稿，未落地、未实测、未改代码**。
> 来源：对照 `senera` v2 的「宿主单一观测压缩管线」（主线 squash `99834b90`，2026-10-13），
> 提取**与语言/技术栈无关**的判据。代码零可移植（TS/Node vs Kotlin/Android），判据可拿。
>
> 相关：`design-memory-retrieval-and-consolidation.md`（记忆分页与页预算）、`design-auto-compaction.md`
> （上下文压缩）、`peer-apps-benchmark.md` §11.3（「先度量判据」的方法论）。

## 1. 这份稿子要解决什么

本仓目前**没有统一的「工具输出 → 模型上下文」预算与降级层**：各工具各自截断，超了**静默丢**，
模型无法区分「这就是全部」与「被裁过」。记忆分页是唯一有预算概念的地方，但它只服务记忆，
而且是**单级限幅**（没有「本轮份额」这一层）。

一句话：**我们缺的不是更小的输出，而是「放不下的那部分怎么被声明和取回」。**

## 2. 现状盘点（带证据）

| 位置 | 现状 | 问题 |
|---|---|---|
| `MemoryTools.kt` `SEARCH_RESULT_CHAR_BUDGET = 6000` | 整体字符预算 | 无「不可裁剪头 / 可裁剪体」之分；超了直接砍 |
| `MemoryConsolidationPrompts.kt` `manualLibraryBudget = clamp(min(window,512K)×60% − 6K − 4K, 4K, 512K)` | **单级限幅** | 没有「本轮均分份额」；连点三次 = 三次全扫（真机实测 297K 输入 / 2 分 28 秒） |
| `ContextLength.kt:125 estimateTokens` | 精确计数（cl100k 可用） | 只算**文本**，不含协议信封/标记/模板开销 ⇒ 偏乐观 |
| 工具结果截断 | 静默丢弃 | **无 `complete` / `omissions` 声明**；模型只能靠"看起来短"猜 |

## 3. 判据（分组，每条给「规则 → 为什么 → 本仓落点」）

### A. 预算与准入

**A1 两级限幅：`min(单次份额, 全局上限)`。**
只给全局上限，一个工具吃掉整个窗口；只给份额，N 个并行调用合起来超窗。
→ 本仓落点：页预算之上再加「本轮份额」，两者取小。

**A2 预留发生在执行之前，且必须在下一个不可逆步骤前结清。**
并发完成顺序不定，事后分配会随顺序抖动 ⇒ 同一批调用重放结果不同。
→ 本仓落点：工具调用批次登记时预留；推进下一轮模型请求前断言「无未结清预留」。

**A3 「预算为 0」是合法降级态，不是错误码。**
把「没额度」当失败会诱导模型重试同一调用，放大消耗。
→ 本仓落点：零额度返回**最小可用信封**（状态 + 指针 + 一句说明），不抛错。

**A4 计量对象必须是「最终会到达模型的完整序列化载荷」，而不是原始结果或估算值。**
只算 result 会忽略信封成本（短结果上占比可达 10–25%）。
→ 本仓落点：一个 `measure(wirePayload)` 唯一入口，禁止各处 `estimate(result)`。

**A5 容量只有一个来源。**
压缩、观测、截断各自推导 reserve ⇒ 边界不一致（一个认为放得下、一个认为超）。
→ 本仓落点：`inputCapacity` 收敛为只读函数，所有预算模块依赖它。

**A6 结构预检先于精确计数。**
对 50MB 输出跑 tokenizer 是 CPU 事故。先判「**必然超**」（如字符数 ≥ limit×4 或字节数 ≥ limit×32），
「可能不超」才付费精测。

### B. 内容选择

**B1 升级信号是「丢了多少内容」，不是「超了多少 token」。**
单一阈值必然出现两类误判：刚好 fit 但语义已被压碎 / 超一点但只多几行。
→ 本仓落点：每次投影打 `complete` + `contentLoss` 两个量，**`contentLoss` 触发升级**，`token` 触发裁剪。

**B2 重复折叠 ≠ 内容丢失。**
500 行相同错误压掉 499 行是**增益**；若计入 loss，所有日志类输出都会无故升级，白烧一次模型往返。
→ 本仓落点：`去重删除` 与 `实质丢弃` 分成两个计数器。

**B3 叶片预算按 `1/√N`，不按 `1/N`。**
均分会先压掉「短但关键」的字段（`cursor_abc123`、`citationId`）——长文档截断最常见的静默失败。
→ 本仓落点：短字段先留、长字段先削。

**B4 信封优先：先扣不可裁剪头，残值给可变详情，并给详情排序。**
信封（类型/状态/坐标）不能删；和详情一起竞争会先挤掉坐标 ⇒ 模型无法回读。

**B5 错误信息属于信封，不参与详情预算的零和竞争。**
错误消息是模型的主要纠正信号；当普通长字符串压掉会让它无法定位修复方向。

**B6 保护原子：URI / 路径 / hash / 错误码 / 版本 / 日期 / 退出码。**
语义或概率式压缩最危险的失败是「两条日志看起来相同，但一个 `exit 0` 一个 `exit 1`」。
→ 本仓落点：压缩前抽「不可合并 token」作硬约束。

**B7 保头保尾 + 关键项优先采样，绝不做均匀截断。**
大输出的有效信息集中在开头（框架/结论）和结尾（错误/汇总），均匀降采样同时丢两端。

**B8 单一摘要所有者。**
两处各写一份摘要 ⇒ 不一致、双倍 token、双倍费用。派生摘要的写权限收到唯一组件。

### C. 声明与信任

**C1 完整性入协议，且「缺省 = 完整」写进 schema，不靠推断。**
模型无法区分「这是全部」和「被裁过」时会反复回读或误信。
→ 本仓落点：跨边界的投影对象统一带 `{complete, omissions[], method}` 三件套。

**C2 外部内容带来源属性 + 信任级别，且先转义后包裹。**
工具输出可能包含伪造的 JSON/XML 结构，破坏线格式；网页正文可能被当指令执行。

**C3 脱敏发生在进入任何派生之前，不是进入模型之前。**
观测会被持久化进会话历史与摘要，晚脱敏 = 秘密已落盘。

**C4 指针字段（可回读原文的句柄）不参与预算竞争。**
裁剪掉坐标 = 不可恢复的信息损失。

### D. 归属与复用

**D1 淘汰配置项要显式退役，不要近似映射。**
把旧阈值映射到新上限，会让老配置产生**含义变化**的静默行为差异。
→ 与本仓刚踩的 `DEFAULT_AUTO_MODEL_ID` 语义变更是同一类问题。

**D2 失败路径与成功路径共用同一条预算/压缩通道，不另开旁路。**
旁路 = 两条输出格式、两套预算、两种被模型误解的可能。

**D3 历史级压缩交给唯一所有者，本层只维护「索引 + 配额」。**
压缩时机需要全局视图，单条结果层看不到；但**必须把句柄索引交给它**，否则压缩后无法回读。

## 4. senera 的实证与它自己的坑

**它验证了**：四级流水线（`verbatim → mechanical → llm → pressure`），升级由**内容损失**触发；
单观测上限默认 16,384 token（旧版 per-tool 投影是 64k 级）⇒ **单观测上限从 64k 降到 16k 是最硬的行为变化**；
「缺省 = 完整」让完整观测零成本。

**它踩了（我们必须避开）**：

1. **压缩器抛错污染执行结论** —— `compress()` 内任何异常经 catch 走到 `projectFailureResult`，
   **把一次成功的工具执行改写成 failure observation**。
   ⇒ 必须把「观测构建失败」与「工具执行失败」分成两个维度（`execution_status: completed` +
   `output_availability: partial`），否则用户看到「命令失败」而实际成功。
2. **一批无读者的死字段**（预算记账字段写了没人读、依赖零 import）—— 本仓也有过同类（`read_count`）。
3. **协议升级靠删会话文件**（不是迁移）—— 升级前必须知情。
4. **没有「每轮最多 N 次 LLM 摘要」的计数上限**，只有预算护栏。

## 5. 本仓落地建议（未排期）

| 阶段 | 内容 | 风险 | 依赖 |
|---|---|---|---|
| 1 | **完整性声明（C1）+ 保护原子（B6）+ 保头保尾（B7）** | 低 | 无 |
| 2 | **两级限幅（A1）+ 预留结清（A2）+ 载荷计量（A4）** | 中 | 需要统一的调用批次概念 |
| 3 | **分级降级（B1/B2）+ 单一压缩器（B8/D3）** | 高 | 前面两阶段先稳 |

阶段 1 单独就有价值：**「超预算就静默丢」本身就是缺陷**，声明成本极低。

## 6. 明确不做

- **不引入 LLM 摘要级**，除非实测证明机械级不足（senera 那级要一次完整模型往返、串行 await 在工具结果路径上）。
- **不照搬 20 条全量**：`1/√N` 叶片预算（B3）在我们「按记录顺序分页」的模型下不适用，
  只有将来做工具输出内容级裁剪才需要。
- **不引入外部压缩库**（`@agent-context/sift` 这类 N-API 原生插件），Android 上属于新 ABI 面。

## 7. 边界与未验证

- 本文所有判据来自**读 senera 代码 + 文档**，**没有在真机上验证过任何一条**。
- senera 的 `@agent-context/sift`（N-API 原生插件）内部行为**全是反推**（无 `node_modules`、外网被阻断），
  不可当事实；本稿也不依赖它。
- 它的「无产物模板的工具在不 fit 时会失去内容」是**待验证结论**（代码路径 + 单测支持，无端到端实测）。
- 本稿**未跑任何基准**：阶段 1 落地前应先度量「当前有多少工具输出真的超预算、超多少」，
  否则可能修一个不存在的瓶颈（参考 `peer-apps-benchmark.md` §11.3 的教训：**判据不是杠杆，预算是**）。
