## 0. 一句话

现状压缩是「逐条截断 → 分块并行独立摘要 → 拼接」；本文把它改成「**滚动携带的分块摘要**（第一步，直接落地）+ **锚点精炼遍**（第二步，快速模型）+ **语义分段**（第三步，暂缓）」，并明确与上下文净化的分工——**关联在判据库，不耦合在流程**。

## 1. 现状与三个损失点

`compressToCheckpoint`（`ChatService.kt:2214-2319`）的摘要流水线：

```
待压缩消息（可能数百条）
  → summaryAsText(maxLength = 2000) 逐条转文本     ← 损失 ①
  → splitIntoChunks(256 条/块) 并行独立摘要        ← 损失 ②
  → joinToString("\n\n") 拼接 = 最终摘要            ← 损失 ③
```

| # | 损失点 | 位置 | 说明 |
|---|---|---|---|
| ① | **单条截断**：每条消息只取前 2000 字符，超出部分任何后续步骤都救不回 | `ai/.../ui/Message.kt:201-208` | `text.take(maxLength) + "..."` |
| ② | **块间失忆**：块并行、彼此独立，跨块指代断裂（人名/任务/文件在第 2 块首现、第 5 块再提时模型不知它是谁） | `ChatService.kt:2284-2288`、`CompressionPlanner.kt:91-100` | 且 prior 检查点被**每个 chunk 重复注入**（`ChatService.kt:2252-2257` 的 `additional` 对每块都 append `priorContext`），N 块 = N 份「请与 prior 合并」的半成品再拼接 |
| ③ | **无整体校验**：块间矛盾、重复、漏关键事实直接入档；检查点是**永久**载体（`trimCompressionCheckpoints` 清旧行，摘要合并前进） | `ChatService.kt:2288`、`:2309-2310` | 拼接 ≠ 合并 |

并行设计的初衷是**速度**；代价是精度。本文的三步都在这个权衡里做文章。

### 1.1 一个决定耦合面的事实：摘要输入只取 Text part

`summaryAsText` 的 `when (part)` 里**只有 `UIMessagePart.Text` 产出文本**，`Reasoning` / `Tool`（含输出）全部为空串。即：

- **推理残留不进压缩输入**（净化稿的主目标物在压缩这里天然被丢弃）；
- 工具轮（`[Text, Tool, Text]` 形状）进摘要的只有两段文本，调用与结果本身不进。

这决定了 §6 的结论：压缩与净化的真实重叠面只有 **Text part 的字面重复**（退化泄漏进正文时），比直觉小得多。

## 2. 方案总览

| 步骤 | 解决什么 | 成本 | 改动面 | 建议 |
|---|---|---|---|---|
| 1. 滚动摘要 | ②块间失忆 + prior 重复注入 | 并行→串行（块数通常 1~3，延迟增幅可控） | `compressChunk`/合并块约 20-30 行 + prompt 一段 | **先行落地** |
| 2. 精炼遍 | ③无校验 + ①的兜底 | +1 次 LLM 请求（输入仅摘要+锚点，几百 token，可走快速模型） | 新函数 + 一次调用 | 第 1 步观察一版后上 |
| 3. 语义分段 | 让块边界对齐话题边界 | 纯本地，零请求 | 新分段函数替换 `splitIntoChunks` 调用点 | 暂缓（长会话才明显） |

三步**正交可独立落地**；第 2 步依赖第 1 步的锚点产出（顺带），第 3 步谁都不依赖。

## 3. 第 1 步：滚动摘要（rolling map-reduce）

### 3.1 算法

```
carry = prior 检查点（可为空）
for chunk in chunks:                 // 串行
    Si = LLM(压缩提示词 + chunk + carry)   // Si 是「合并摘要」，不是增量
    carry = Si
最终 = carry (= Sn)
```

- prior 检查点只作为**初始 carry** 注入一次（现状是每块重复注入、产出 N 份半合并——顺带消除）；
- 每块的提示词里 carry 走现有 `{additional_context}` 占位符（`ChatService.kt:2268-2273` 的 `applyPlaceholders` 不用改），措辞加一段「PRIOR SUMMARY（与本块合并为单一摘要，不要分段拼接）」；
- 用户 `additionalPrompt`（手动压缩的附加指令）每块保留注入（它是约束不是内容，重复无害）。

### 3.2 顺手修：超长单条独占 chunk（针对损失 ①）

`summaryAsText(maxLength = 2000)` 对超长正文最粗暴。改为：**转文本阶段检测单条超阈值（建议 8000 字符）的消息 → 该条不截断、独占一个 chunk**（上限仍设绝对帽，如 64K 字符，防止把摘要请求本身撑爆；超帽仍截断并标记 `[truncated]`）。分块仍走 `splitIntoChunks`，只是「条→文本」的粒度多一档。

### 3.3 失败语义

现状 `awaitAll`：任一块失败 → 整体失败（async 异常传播）。滚动版第一版**沿用 fail-fast**：第 N 块失败丢弃已生成的 S1..S(N-1)，整体重试。理由：压缩是幂等副作用安全的操作（落库前失败不产生半检查点），断点续跑是纯优化，等真实会话块数分布证明有必要再做。待讨论项见 §7-1。

### 3.4 延迟账

- `COMPRESS_MAX_MESSAGES_PER_CHUNK = 256`（`CompressionPlanner.kt:33`）意味着**多数会话只有 1 块**——1 块时滚动 = 现状，零回归；
- 2~3 块的长会话串行化后总时长 ≈ 各块之和（现状 ≈ 最大块）；配合 `runCatching` 外层与后台触发（自动压缩不打断发送），用户可感影响限于手动压缩的等待。

## 4. 第 2 步：精炼遍（refine pass）

### 4.1 锚点机制

第 1 步的压缩提示词**顺带要求**在摘要末尾输出「锚点清单」——本轮出现的关键事实（用户称谓/决策/未完成任务/精确数值/文件与路径），逐条一行。精炼遍输入 = `Sn + 锚点清单`，指令：「核对以下摘要是否覆盖每条锚点、有无自相矛盾或重复段落，输出修订版」。

- 覆盖不了锚点的（第 1 步丢了）→ 指令为「列出缺失项 + 从摘要可见信息尽量补写，仍不可得则标注 (lost)」——不假装能找回；
- 模型：**快速模型**（`settings.fastModelId`，已有基建 `resolveCompressionModel` 同款回退语义），输入几百 token，秒级、近零成本；
- 锚点清单**不入档**，只是中间产物（检查点仍只存摘要正文）。

### 4.2 廉价保险：containment 自检（与净化判据库的第一个交点）

滚动摘要的已知风险是**污染传播**：某块若含字面重复正文，其摘要的垃圾会随 carry 传给后续所有块。保险：每生成一个 `Si`，本地跑一次字面重复判定（containment ≈ 1 / 周期检测，判据函数与护栏、净化同源，见 §6.4）；命中则该块降级处理——**丢弃 Si、该块原文直接跳过压缩（在最终摘要中标注 `[skipped: degenerate]`）**，carry 保持上一个值继续。

这是「输出侧检查」的第一版；净化落地后可升级为「输入侧预清理」（Text part 预剥离再进摘要）。两者共用判据库，不共用流程。

## 5. 第 3 步：语义分段（暂缓）

按话题边界切块：信号候选 = 相邻消息时间间隔突增 / 会话内标题变化 / 关键词分布突变。纯本地规则，零请求。暂缓理由：第 1 步的滚动携带已大幅缓解「块边界切断话题」的代价（后块能看到前块摘要），分段的边际收益集中在话题跨度极大的会话，先拿数据说话。

## 6. 与上下文净化的关联（供并行会话讨论）

> 本节为跨设计接口，结论：**关联在判据库，不耦合在流程**。净化稿的工作区草稿（revision 3）未读全，锚点以其定稿为准。

### 6.1 触发口径的隐性耦合（最实际）

`estimateWindowTokens`（`ContextLength.kt:58-73`）**优先取真实 `promptTokens`**，本地兜底才用 `estimateTokenCount`。两路径对推理残留的口径**不一致**：

| 路径 | 残留计不计 | 后果 |
|---|---|---|
| 真实 usage（优先） | **计**（OpenAI 兼容默认回传 `reasoning_content`，provider 侧计入 promptTokens） | 一次严重退化抬高占用读数 → **提前把会话顶过压缩阈值**，提前触发一次不可逆检查点 |
| 本地兜底估算 | **不计**（`ContextLength.kt:82-92` 只算 Text + Tool 输出） | 同一会话两路径给出不同占用 |

净化落地后会降低后续轮次实发 token → 占用读数回落 → **净化间接参与压缩触发决策**。分歧本身值得在净化稿记一笔（净化后发送内容与估算口径大致对齐，现状不是）。

### 6.2 接力关系：压缩边界是残留的「终点站」

- 净化管**在途**：上一轮窗口（`u_prev, u_last`），治理「自己教自己」；
- 压缩管**终点**：残留随轮次越过检查点边界后被 Text-only 摘要**永久丢弃**（§1.1）；
- 净化窗口够不着边界前的老残留——那部分由压缩天然兜底。**两层防御接力，无冲突需要协调**；净化稿「压缩管预算，净化管质量」在代码层即此形状。

### 6.3 唯一真实重叠：Text part 字面重复

退化泄漏进正文（Text part 重复）时会以「前 2000 字」进摘要输入，滚动化后还会**向后传播**（§4.2 保险的动机）。注意：净化规则表（C1 系）管 Reasoning 累积与工具空转，**Text 重复也不在它的规则表里**——两边都需要判据库的新增消费者，而不是谁覆盖谁。

### 6.4 判据库：一库三消费者

```
字面重复判据（containment / minimalPeriod / distinctChars，护栏已 internal）
  ├─ 护栏：调用内/边界停止
  ├─ 净化：发送副本 part 级剥离（设计稿 §4.2 计划同源）
  └─ 压缩（本文新增）：§4.2 输出自检 → 将来输入预清理
```

净化稿已计划与护栏同包共享；本文作为第三个消费者接入，**不新建判据**。§4.2 的 containment 阈值是否直接借用净化标定值（0.8 一档）→ §7-3。

## 7. 待讨论问题（拿去并行会话）

1. **滚动失败语义**：fail-fast（本文推荐，第一版）vs 断点续跑（保存 carry 逐块重试）——需要真实会话的块数分布数据；
2. **精炼遍模型**：快速模型（本文推荐）vs 压缩模型本身（少一次模型切换，但慢）；
3. **containment 阈值**：借用净化标定值 vs 摘要场景单独标定（摘要文本与推理文本的重复率基线可能不同——摘要本身就高度浓缩，误杀风险方向相反）；
4. **触发口径分歧行为**（§6.1）：usage 计残留 vs 估算不计，要不要统一、往哪边统一（倾向：等净化落地后自然对齐，不单独动）；
5. **超长单条的绝对帽**（§3.2）：64K 字符是否合适，或按压缩模型窗口动态取；
6. **锚点清单格式**：自由文本 vs 固定 schema（`- [fact] ...`），固定格式利于精炼遍核对但可能限制摘要模型的表达。

## 8. 测试计划

- **单测（纯函数）**：滚动合并逻辑（carry 传递/prior 单次注入/失败传播）；超长单条独占 chunk 的分块；containment 自检的降级路径（命中→跳过→carry 保持）；
- **单测（prompt 契约）**：`additional_context` 内容在滚动版每块的形态（prior 仅首块、carry 其后、additionalPrompt 每块）；
- **仪器/真机**：手动压缩一个多块长会话，对比新旧摘要的连贯性（人工评估）；`PromptInspectPage` 检查点预览确认注入形态；
- **回归**：单块会话行为与现状逐字节一致（1 块 = 旧路径，仅 prior 注入位置变化）。
