## 装配性能

同一设备、同一测试进程、相同 25 个 JSON 插件；两种装配模式先各预热 200 次，再交替记录 500 次，
只构建列表，不执行转换器/脚本/网络。记录代码在 `TransformerChainInstrumentedTest`。

| 分支 | median | p95 |
|---|---:|---:|
| 原有声明顺序 | 0.048177 ms | 0.058750 ms |
| 注册阶段排序 | 0.068177 ms | 0.081615 ms |

注册分支 p95 增加约 0.022865 ms；不将此结果描述为性能提升。
采样前固定护栏为 `registered p95 <= max(4 * legacy p95, 2ms)`，最终通过。
原始日志：`legacyMedianNs=48177 legacyP95Ns=58750 registeredMedianNs=68177 registeredP95Ns=81615`。
这只验证同一实现下排序/筛选的装配成本；不是重构前后完整 APK 的性能对比。

## 模型目录契约对照

| 维度 | 当前实现/证据 | P1c 结论 |
|---|---|---|
| 查询协议 | `ai/provider/Provider.fetchModelCatalog`；`CatalogFetchResult` Complete/Partial/Failed/Unsupported；`ModelCatalogTest` 16 项 | 已有窄契约，复用，不建第二套目录 DTO |
| 生命周期 | app `ProviderModelCatalogRepository` 持有进程作用域、共享 job、全局并发限制；取消单个等待者不取消刷新 | 所有权应留宿主，不交给单个插件页面 |
| 凭据隔离 | scope 指纹、旧凭据迟到结果丢弃、登录更新/新会话区分；仓库合约测试覆盖 | 不把凭据交给通用插件运行时；Provider 路由维持现有实现 |
| 持久化 | `CatalogSnapshotStore` 独立缓存；保留 lastComplete，记录中断/写盘失败 | 是可重建缓存，不新增 Settings 字段或备份条目 |
| 消费者 | 当前目录页面、模型列表/缺失告警只消费该仓库；本轮没有第二个动态替代者需求 | 目前契约足够，保留 `ai` 协议 + app 仓库，P4 有真实消费者再评估提取 |

## 验收边界

P1c 代码与上述自动化检查完成；独立 Application 的 instrumentation 不代表生产 UI/DI 全链路验收。
尚未验证人工流式聊天 UI、后台恢复、端到端首 token、峰值/驻留内存、WebView 创建次数的完整对照。
不据微基准补写这些缺失指标，也不把未执行项标成通过。P1 决策门和回滚窗口收尾仍单独进行。
