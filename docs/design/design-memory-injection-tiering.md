# 记忆注入的分层与位置设计（L0–L3）

> 状态：**第 1 步（L0+L2+L3）已落地**；**第 2 步 L1 已落地一半**——DB/模型/渲染/接线/守卫
> 与「固化记忆」入口均已完成（真机可标记锚点），**尚缺「会话开始冻结」**。2026-10-15。
> 决策来源：真机实测（见 §2）+ 用户拍板（§5 的 L1 刷新触发点）。

## 1. 问题：记忆一变，整个前缀缓存全废

`PromptAssembly` 把记忆块放在**唯一那条 system 消息内部**（`SystemBlockSource.MEMORY`，位于 PERSONA 之后、
TOOL 之前），而 provider 的前缀缓存**从位置 0 起连续匹配** —— system 是最前面那条消息，改它任何一个字节，
整条 system 失配 ⇒ **其后全部不命中**。

`PromptInspectPage.kt:354` 早就写下了这条约束：

> 前缀缓存提示：system 在位置 0，**任何随会话变化的内容出现在 system 里都会让整段缓存失效**

## 2. 真机实测（2026-10-15，DeepSeek-flash，同一会话连续 5 轮）

方法：新建临时会话 → 逐轮发送并读消息下方 NerdLine 的 `(Y cached, Z%)` → 第 3 轮让模型写入一条记忆
（模型实际调用 `memory_tool` 创建成功）→ 第 4 轮读数 → 第 5 轮作**对照组**排除"缓存自然过期"。

| 轮 | 事件 | prompt | cached | 命中率 |
|---|---|---|---|---|
| 1 | 首次请求 | — | 0 | 0%（无前缀可命中） |
| 2 | 稳态 | 7.6K | 7.4K | **98%** |
| 3 | 本轮内写入记忆（**生成开始时的快照**，当轮不可见） | 7.9K | 7.7K | **97%** |
| **4** | **记忆已变** | 8.0K | **0** | **0%** |
| 5 | 恢复稳态（对照组） | 8.0K | 7.8K | **98%** |

日志交叉验证：`memory inject: 1/1 memories ≈278 tokens` → `2/2 ≈301 tokens`（记忆确实变了）；
第 3 轮同一轮出现两条注入日志且条数不变（印证「生成中快照」）。

**结论（比预估更严重）**：一次记忆写入 = **整个 prompt 全量重算**，而不是"记忆之后的部分"。
本次记忆本身仅 **301 token**，却导致 **8.0K token** 全量重算。失效量 = 整个 prompt ⇒
**随会话长度线性放大**（50K 会话写一次记忆 ≈ 50K token 重算），而记忆是**模型主动写**的
（成本 = 会话长度 × 写入次数）。

## 3. 设计：按「层级 → 位置」注入

**判据不是"重要 → 放 system"，而是"可能变 → 必须放尾部"。** 层级与位置一一对应：

| 层 | 内容 | 波动性 | 位置 | 配额 |
|---|---|---|---|---|
| **L0 纪律** | 静态使用纪律文本（现 `buildMemoryPrompt` 的那段英文声明） | **恒定** | system | 固定 |
| **L1 锚点** | 身份/权威类记忆（"我是谁""用户是谁""铁律"） | **冻结刷新** | **system** | 小（3–5 条） |
| **L2 工作集** | 本轮相关记忆全文（**可依赖当前查询**） | 每轮可変 | **tail** | 预算内 |
| **L3 索引** | 其余记忆一行（`id ｜ description ｜ 更新日`） | 写入时变 | **tail** | 预算内 |

### 3.1 缓存代价（可控且显式）

| 层 | 代价 |
|---|---|
| L0 | 0（恒定） |
| L1 | **每次刷新一次全量失效** —— 频率由刷新触发点决定（见 §5） |
| L2 + L3 | **0** —— 在尾部，怎么变都不影响前缀 |

对比现状（§2 实测）：普通记忆写入的代价从「一次全量失效」降到 **0**，只有锚点刷新才失效。

### 3.2 顺带解开 relevance 的死结

L2 在尾部 ⇒ **可以依赖当前查询、每轮重算、每轮换集合**，不再与缓存目标冲突。
此前"relevance 与保缓存互斥"的结论，前提是"记忆块留在 system"；位置一变，结论即变：
**前缀稳定归 L0/L1（头部），查询相关性归 L2（尾部），两者不再抢同一块地。**

### 3.2.1 落实（2026-10-16）

**做了什么**：`data/ai/MemoryRelevance.kt`（新）——查询 = 发送窗口里**最后一条真实用户消息**
（合成消息不算：压缩检查点也是 role=USER，且本层的记忆块自己就是合成 USER，不排除会"自己算自己"）；
相关性 = **词元重叠的覆盖度**（查询词元被该记忆覆盖的比例）。`selectMemoriesForPrompt` 的
入选分改为 `memoryScore × (1 + 1.0 × 相关性)`。

**为什么不用 embedding**：判据只要能回答"这条记忆讲的是查询这件事吗"。记忆条目短、查询同语言，
共享实词就已经是很强的信号；向量相似度要额外背一个模型/一次请求/一份不确定性，换来的分辨力
在本场景用不上。**本地词元重叠还有一个决定性的好处：逐字节可复现**——同一查询同一集合必然
产出同一段文本，缓存行为和单测都能钉住。

**中文没有词边界 ⇒ bigram**：CJK 取相邻二字（"记忆"/"渲染"/"咖啡"），拉丁按词切。两级词元
（bigram + 非虚词单字）**匹配时不能混用**——第一版只给查询做了单字兜底，于是"猫"这种单字查询
拿去和长记忆的 bigram 比永远匹配不上；`single character cjk query still works` 抓出了这个真 bug，
现在查询只有单字时，两侧都退到单字级别比对。虚词只挡"两个都是虚词"的组合（"的是""我们"），
"记忆"这类实词组合必须留。

**两条保守性设计**（不确定时一律退回改动前的行为）：
1. **只抬不压**：乘性增益，无词汇重叠时增益 = 1.0 ⇒ 打分与改动前**逐位一致**。
   刻意不用相关性去**淘汰**记忆：像"我是素食者"这种身份型记忆本来就不该与查询有词汇重叠，
   拿相关性当闸门，第一批被淘汰的正是最该留住的那批（importance 存在的理由）。
2. **低于 `RELEVANCE_FLOOR`(0.1) 视为无证据**；分母封顶 `QUERY_TOKEN_CAP`(24) 以免长消息
   把真实命中稀释成 0.03。合起来的语义：**短查询更精确（1 个词元即可），长查询需要更多证据**。

**刻意不套分桶**：`SCORE_BUCKET_SIZE` 是为 system 时代的"分数连续漂移打掉前缀缓存"服务的；
L2 已不在前缀里，套桶反而会让"同桶内按写入先后"盖掉相关性（差分不到一档就不提升 = 白算）。

**顺带修掉一处会撒谎的地方**：`ChatService` 那条 `memory inject: N/M memories` 日志也在调
`selectMemoriesForPrompt`。接入相关性后若不传查询，它会用**另一套口径**算出条数 ⇒ 日志与实际
注入不符，而这条日志是判断"记忆吃了多少 token"的唯一依据。现在它按**同一份消息**（新提的局部
`promptMessages`）推查询。

**验证**：`MemoryRelevanceTest` 11 条（查询派生 / 中英相关性 / 单字兜底 / 虚词不算证据 /
长查询不稀释 / **无查询逐位一致** / 相关性真的改选 / 相关性把低于下限的记忆救回 / 相关性不得
挤掉身份型记忆 / 同查询逐字节一致）；`PromptAssemblyTest` 新增 1 条走**完整装配**的接线用例
（紧预算下问"渲染器"选 TikZ、问"咖啡"选咖啡——只看**全文层**，因为落选的那条照样会以清单行
出现）。两处注入式反证各精确变红：把增益写成 1.0（维度静默失效）⇒ 3 条红；装配侧不传 query
⇒ 接线用例红。全量 `testDebugUnitTest` **1541 项 0 失败**。
真机：装机后打开容量面板（它跑的正是 `inspectPromptAssembly` 这条同源装配路径）正常出数，
「尾部记忆（对话末尾）」317 tokens / 4.1%，无异常。

### 3.3 位置的最优解：追加在尾部，而不是插在用户消息之前

前缀收益对位置敏感（记第 N / N+1 轮请求序列）：

- **追加最末**：`sys, h…, userN, MEM_N` → 下一轮 `sys, h…, userN, asstN, userN+1, MEM_{N+1}`
  ⇒ 命中前缀到 `userN`，**最大**。
- **插在 userN 之前**：`sys, h…, MEM_N, userN` → 下一轮该位置是 `userN`
  ⇒ **在 `h…` 就分叉，白丢一个 userN**。

**实现取向**：把 L2/L3 文本**追加到最新用户消息的 content 上**，而不是新造一条消息 ——
避免 Anthropic「对话中途不允许 system role / 连续同 role」这类 provider 差异。
（若改成独立合成消息，须逐 provider 验一遍 role 合法性。）

「工作集」天生每轮变，必须去尾部。本设计是把这套分层**显式映射到注入位置**。

## 5. 决策（用户拍板）

- **L1 刷新触发点 = 会话开始时一次 + 用户手动「固化记忆」**（不做每 N 轮自动刷新）。
  理由：把失效频率变成**显式且可预期**的 —— 每个会话至多一次自动失效，其余由用户主动触发。

### 5.1 冻的是「集合」，不是「文本」（实施中修正，2026-10-16）

原计划把 L1 渲染好的**文本**冻进会话（§8 第 2 步的"或改为传已渲染好的 L1 文本"）。
实施时改成冻**锚点 id 集合**、文本按当前内容实时渲染。触发修正是记忆库里的
**两条自动删除路径**：

- `MemoryConsolidationGenerationAgent`（做梦整理）会 `deleteMemory`；
- `MemoryRepository.enforceMaxCount`（200 条上限）按分数淘汰，**锚点并不在豁免名单里**。

这两条都不会去逐个刷新会话。冻文本的话，一条被删掉的锚点会**永远**留在 system 里
——既忘不掉（模型继续看到它），也改不动（用户改内容也不生效）。而存 id 则：

| | 冻文本 | 冻 id 集合（现方案） |
|---|---|---|
| 新固化一条锚点 | 不影响本会话 ✓ | 不影响本会话 ✓ |
| 删掉一条锚点 | **永远留在 system** ✗ | 立刻消失 ✓ |
| 改写锚点内容 | **不生效** ✗ | 立刻生效 ✓ |
| system 字节稳定性 | 集合与文本都不变才稳定 | **只由集合决定** |

「改写立刻生效」看着像削弱了冻结，其实是回到 §5 的原意：用户按「固化记忆」按钮表达的是
**"以后哪几条算数"**，而不是"顺便把当时的措辞也钉死"。被冻住的是集合 ⇒ 新固化/取消固化
不会悄悄冲掉所有会话的前缀缓存，这正是 §5 要买的东西。

## 6. 数据模型改动

1. `is_anchor: Boolean`（或 `authority_level: Int`）—— L1 入选依据。
   **照抄 bigeye 的安全约束：禁止 AI 自填，只由整理器/用户提拔。**
2. `pinned: Boolean`（或复用 importance 阈值，bigeye 7.0/10 ≈ 本仓 0.7）—— 免衰减 + 免淘汰。
3. 可选：`layer` / `epistemic` —— 暂不加，等有明确消费者再说（避免"预留字段变技术债"，
   这是 bigeye 自己的教训：`MAX_OBS_PER_PAGE` 零引用且与注释矛盾）。

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| **L1 冻结会陈旧**（会话中途用户改口，system 仍断言旧版本） | L1 只放**低变动率**内容（身份/铁律）；"用户改口"由 L2 覆盖 |
| **L2 降到尾部后遵循度下降**（system 权重高于历史） | A/B 验证；这正是 L1 存在的理由——把真正需要权威感的几条留在 system |
| **契约测试要改** | `PromptAssemblyTest` 锁着 `joinToString("\n")` 的逐字节契约，属预期成本（用户已确认可接受） |

### 8.2 固化入口的作用域：两个都显式，去掉静默刷新（2026-10-16，`5fb401e4b`）

用户提出「手动的记忆固化改为会话级？」。同意，并确认连带要处理「记忆页改锚点时的顺带刷新」——
留着它两个入口会打架。**最终取 B：两个作用域都由用户显式选，且没有任何静默行为。**

| 入口 | 作用域 | 位置 |
|---|---|---|
| 「本对话固化记忆」 | **这一条**会话 | 会话菜单（长按会话行），紧挨「本对话不使用记忆」 |
| 「固化记忆」 | 该助手的**全部**会话 | 助手指记忆页（做梦整理卡片下方） |

- **会话级为什么值得单列**：助手级会让该助手**每条**会话在下次回来时各吃一次完整的前缀
  miss，而那往往是冷启动、最需要命中的时刻。会话级把代价限制在「你主动选中的那一条」。
  两者是同一笔总代价的两种支付方式（批量 vs 按需），区别在于**未使用的会话不必先付**。
- **去掉静默刷新（本批关键）**：`AssistantDetailVM.updateMemory` / `addMemory` 不再顺带
  调用 `refreshFrozenAnchorsForAssistant`。此前「点一下『固化为锚点』开关 ⇒ 该助手所有会话的
  缓存被静默作废」正是这套分层要消灭的形态。改锚点现在**只影响新会话**（新会话开始时按当时
  集合冻结）；已有会话要采纳，必须有人**按下**上表两个入口之一。这正是 §5「把失效频率变成
  显式且可预期」的落地。
- 三处冻结路径（会话开始 / 会话级固化 / 助手指级固化）共用 `ChatService.currentMemoriesFor`，
  让「同一口径」**结构上**成立，而不是靠三处各写一遍。
- 文案连带订正：`assistant_page_memory_anchor_hint` 原文「改动它会让整个前缀缓存失效」在冻结
  之后**不再成立**，6 locale 全部改写为「只对新会话生效，已有会话要在会话菜单里按固化」。
- 守卫：`MemoryAnchorWiringTest` 新增两条源码豁免/接线检查（改锚点不得静默刷新、会话菜单
  必须接到 `freezeAnchorsForConversation`），各以注入式反证确认精确变红。全量 1527 项 0 失败。

### 8.3 会话内的记忆入口（2026-10-16，`ChatInput` 图标行）

**缺口**：在此之前，两个记忆控制**只存在于抽屉的会话列表长按菜单**里 —— 聊天页本身没有任何
入口。用户想给「这个对话」关记忆或固化锚点，得先退到抽屉、长按那一行。

**做法**：输入栏图标行加一个「记忆」按钮（`ui/components/ai/MemoryPicker.kt`），
**排在上下文占用读数的右侧**（两问相邻：*已经用了多少* / *记忆这块用不用、要不要冻结*）。
点开是紧凑的两行选择器，与抽屉菜单**同款文案**：

1. 「本对话不使用记忆」—— 带勾选态，复用 `chat_memory_disabled_toggle` + 既有 toast 两条；
2. 「本对话固化记忆」—— 动作项，复用 `chat_memory_freeze_action` + `chat_memory_freeze_toast`。
   （因此本批**不需要新增任何译文**。）

**为什么是一个按钮 + 选择器，而不是两个裸按钮**：两个动作性质不同 —— 隐身在 UI 上必须
**一眼可见**（所以状态直接做在图标上：`Incognito` = 本对话不碰记忆库，`Brain02` = 正常，
并由 `ToggleSurface` 的着色强化），固化则是**一次性动作**、不需要常驻一个图标位。
"点一下切隐身、长按固化"这种分法没有发现性（用户不会去猜能长按）。
抽屉菜单里那两项**保留**：它们作用于任意一行会话，是这个按钮够不到的地方。

**真机验证（已通过）**：按钮出现在占用读数右侧、排版与相邻图标一致；点开显示两行；
点固化 → toast「已在本对话固化 1 条锚点」；点隐身 → 图标变 `Incognito` 且去色。
