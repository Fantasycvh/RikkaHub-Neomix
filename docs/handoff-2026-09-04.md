## 三、#1812 半截回复保留设计（`docs/design-partial-failure-draft.md`）

**状态**：**已实现**（`20d84333`，2026-09-04），**待真机测试**。同批吸收 B1（空 tool schema 归一化）/B3（workspace stdin EOF）。

**核心分流**：零输出失败（开局即断、无 token）→ 自动重试照旧；半截输出失败（已流式合并可见内容后断）→ 不再自动重试，保留为草稿交用户决定。

**三层落点**（已对照代码核实，行号见设计稿）：
1. **GenerationHandler**：流式 catch 块（GenerationHandler.kt:519）回滚前保存 `partial = messages`；**半截判定必须在 catch 块内**（只有它能见 messages）；构造 `GenerationPartialFailureException(cause, partialMessages)` 抛给 `withGenerationRetry`，后者识别该类型**直接 rethrow 不重试**；阈值 = 过滤 reasoning 后最后一条 assistant 消息可见 Text ≥ 50~100 字符（可配）。
2. **ChatService**：catch 到该异常 → 半截消息进当前 MessageNode 候选 #0（复用 regenerate 机制，成功后自然成候选 #1，无需新 UI 分支）→ 立即 `saveConversation`（这是**失败路径第一个写库点**，suspend 可在 `onFailure` ChatService.kt:696 直接调）→ 发软提示而非 error 卡片。
3. **UI 标记**：方案 A（推荐）`UIMessageAnnotation {type:"partial_failure"}`，客户端元数据不进 API 上行；方案 B 备选参考 rikkahub-agent `2945c612`。

**关键代码事实**（"为什么连一次生成都没留下"）：
- 流式过程只写内存：`updateConversation` → `session.state.value =`（ChatService.kt:997-1002），生成期间从不落库；`saveConversation` 只在 `onSuccess`（ChatService.kt:706）。
- 重试 = 每次清空半截：流式 catch `messages = snapshot` 回滚（:519-524，snapshot 是生成前干净状态 :500）。
- 重试耗尽后半截已不在内存，`onFailure` 只 `addError`（:696-703，纯内存错误列表），失败/重试路径零落库。
- usage 已 `merge` 进最后一条消息（:511），随草稿保留零成本、不重复计费。
- 同一"尽早持久化半截状态"机制同时缓解 #1820（切对话回复消失）。
