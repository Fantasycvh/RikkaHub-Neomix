## 二、发布流程（固定）

1. bump versionCode（`app/build.gradle.kts`，**续增不重置**；259 已用）；**设备已装 release 版时不能原地复用同号，必须递增**（否则 `INSTALL_FAILED_VERSION_DOWNGRADE`）。
2. `bash scripts/build.sh release`（自动改名 arm64 产物到 `app/release/`；勿用 `-Pandroid.injected.build.abi`，OOM 用脚本内置 `--max-workers=2`）；**ZCode 会话须带 `GRADLE_OPTS="-Djava.net.preferIPv4Stack=true"`**（修 `FileLockContentionHandler` BindException）。**耗时约 4–5 分钟（R8 + lintVital 是慢步骤），超过本客户端 120s 命令上限——该上限为常态、非临时** ⇒ 须后台跑：写一个包装 .sh（`cd` + `export GRADLE_USER_HOME/PUB_CACHE/GRADLE_OPTS` + 调 `build.sh release` + `echo EXIT=$?`），`nohup bash 包装.sh > 日志 2>&1 &`，再分次 `sleep 100 && tail 日志` 轮询至出现 `APK ready:` 与 `EXIT=0`。⚠️ 被超时中断的构建会在 `app/build/outputs/apk/release/` 留下**上一版的陈旧 APK**（v1.0.12 构建中断后那里是 268 的产物）——故下一步 aapt 核实不可省，且**必须按 versionCode 判断，不能按文件是否存在**。
3. aapt 验证 versionCode/架构；**`app/release/` 可能残留同名旧 APK，务必先核实 versionCode 再上传**。
4. debug 先装机实测 → 草稿：新建用 `gh release create vX.Y.Z --draft -R androidrik/rikka2-my_feature_open`；**替换既有草稿同名 tag 的资产**用 `gh release delete-asset --yes` + `gh release upload` + `gh release edit --title/--notes-file`（双语 ≤10 条日志，`--notes-file` 需绝对路径）。
5. 用户检查后 `gh release edit --draft=false --latest`（**tag 指向转正那一刻的分支 HEAD**）。
6. **tag 一律带 `v` 前缀**（旧 release tag 多数**不带** v，删除时须用实际 tag 名）。
7. README 下载标注随发布更新（有草稿时写「正式发布 X，草稿 Y」；无草稿只写正式发布）。

- **关键使能条件（使抽象远比看上去便宜）**：四个基类**已各自声明形态完全一致、且都是 `kotlin.uuid.Uuid` 的** `abstract val id: Uuid` + `abstract val enabled: Boolean`，而 search/ai/speech **都已依赖 `:common`** ⇒ 在 common 放 `Enableable { val id: Uuid; val enabled: Boolean }` 时**零个子类型需要改**，只加 4 行（每基类 `: Enableable`）
- **难度**：核心（接口 + `resolveSelected` + 墓碑回填/codec + 保持一个）= **~0.5 天，低风险**（行为等价改造，现有 19 项测试（ASR 6 + TTS 13）转绿即证明）；设置页处理器统一 +1–2h 且**风险最高**（3 处自动改选规则细微不同、搜索是**下标制**）→ **建议不做**；全做 ~1 天。**硬约束**：墓碑已落盘，只能共享编解码助手，**pref key 与 JSON 结构一个都不能动**
- **收益（诚实版）**：**代码量净省仅 ~50–80 行**（53 行 `withEnabled` 必须留——密封类无统一 `copy`；各家族策略与测试也留）⇒ **省行数不是理由**。真收益是：①**3 个易错契约各归一处**（墓碑跳过回填 / 选中项被停用不静默回退 / 至少留一个启用）②第 5 个 A 类家族接入变机械工作 ③契约测试合并
- **实证（最有力的论据）**：`ifEmpty { DEFAULT }` 复活陷阱 —— chat 提供商于 2026-09-09（`9a65223d`）踩过并修掉，但 TTS 的同类代码一直未改，**2026-10-01 我在 TTS 上重新踩了一遍**（`f0db94a6` 才去掉）。知识只存在于各家族的局部代码里，就会重复缴学费；共享 `refillDefaults` 让这类 bug 构造上不可能再犯
- **明确不该统一**：①`withEnabled` 分发（需逐子类 `copy`；**但不是静默失败风险**——`when` 对密封类穷尽，新增子类型会**编译报错**，只是噪音）②各家族运行时语义（助手=归档（既有会话照常可用）/ 搜索=停用即不注册工具 / ASR=「请配置」/ TTS=兜底）——领域策略，保持各自文档与测试、只调用泛型原语 ③助手要**排除**在 `resolveSelected` 之外（语义不同）④B 类 6 处
- **建议与触发点**：**核心做、UI 不做**；不急，建议触发条件=「下一个 A 类家族需要墓碑」或「出现第 5 个 A 类家族」。若现在做，可顺手修掉现有不一致（聊天提供商回填仍内联）。最小一步（`Enableable` + `resolveSelected`，把「不静默回退」契约钉进一处）约 1–1.5 小时

**MCP「本地进程拉起」探讨定论（2026-09-12）**：fork MCP 仅 sse/streamable_http 两种远程 transport，无 stdio/本地类型；「先拉起进程再重连」需新增配置类型 + 常驻进程管理器（前置=AI 后台任务三件套），**用户决策不做**，仅落地状态区分（三.1）。若未来立项，形态建议=proot 内 HTTP server + 伴随启动命令字段（transport 层零改动）。
