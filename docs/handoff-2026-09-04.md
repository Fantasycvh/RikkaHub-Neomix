## 二、发布流程（固定）

1. bump versionCode（`app/build.gradle.kts`，**续增不重置**；259 已用）；**设备已装 release 版时不能原地复用同号，必须递增**（否则 `INSTALL_FAILED_VERSION_DOWNGRADE`）。
2. `bash scripts/build.sh release`（自动改名 arm64 产物到 `app/release/`；勿用 `-Pandroid.injected.build.abi`，OOM 用脚本内置 `--max-workers=2`）；**ZCode 会话须带 `GRADLE_OPTS="-Djava.net.preferIPv4Stack=true"`**（修 `FileLockContentionHandler` BindException）。**耗时约 4–5 分钟（R8 + lintVital 是慢步骤），超过本客户端 120s 命令上限——该上限为常态、非临时** ⇒ 须后台跑：写一个包装 .sh（`cd` + `export GRADLE_USER_HOME/PUB_CACHE/GRADLE_OPTS` + 调 `build.sh release` + `echo EXIT=$?`），`nohup bash 包装.sh > 日志 2>&1 &`，再分次 `sleep 100 && tail 日志` 轮询至出现 `APK ready:` 与 `EXIT=0`。⚠️ 被超时中断的构建会在 `app/build/outputs/apk/release/` 留下**上一版的陈旧 APK**（v1.0.12 构建中断后那里是 268 的产物）——故下一步 aapt 核实不可省，且**必须按 versionCode 判断，不能按文件是否存在**。
3. aapt 验证 versionCode/架构；**`app/release/` 可能残留同名旧 APK，务必先核实 versionCode 再上传**。
4. debug 先装机实测 → 草稿：新建用 `gh release create vX.Y.Z --draft -R Fantasycvh/RikkaHub-Neomix`；**替换既有草稿同名 tag 的资产**用 `gh release delete-asset --yes` + `gh release upload` + `gh release edit --title/--notes-file`（双语 ≤10 条日志，`--notes-file` 需绝对路径）。
5. 用户检查后 `gh release edit --draft=false --latest`（**tag 指向转正那一刻的分支 HEAD**）。
6. **tag 一律带 `v` 前缀**（旧 release tag 多数**不带** v，删除时须用实际 tag 名）。
7. README 下载标注随发布更新（有草稿时写「正式发布 X，草稿 Y」；无草稿只写正式发布）。

### 2.1 10-05 新增的三条坑（均已实测）

8. **改 notes 会重置 `tag_name`**：draft 上用 `gh release edit --notes-file` 只改 `body`，服务端会把 `tag_name` 打回合成的 `untagged-…`（与 tag 是否已存在无关）。⇒ **固定顺序：先替换/上传资产 → 再改 notes → 最后 PATCH `tag_name`(+`target_commitish`) → 独立 GET 复核**（不能只看 PATCH 的响应）。若在 notes 编辑之后还要 PATCH，必须显式带上 `tag_name`。
9. **PATCH `target` 之后 Publish，tag 落点是「服务端当次采用的值」**：v1.0.21 曾出现「PATCH 过 target 但发布出的 tag 指向更早的值」⇒ 当时用 `git tag -f` + 强推纠正；v1.0.24 的标准路径（draft 阶段 PATCH 到正确 target、`tag_name` 干净）发布后 `ls-remote` **精确落位、无需纠正**。⇒ **判据**：错位只与「target 曾停留在旧值 / tag_name 被重置」这类前置脏状态有关；**但发布后 `git ls-remote --tags origin vX.Y.Z` 核对始终是必做收尾**（它是唯一可信验证）。
10. **验证「重打的包确实含本次改动」不能只看体积/digest**（体积只说明「不同」）：查 R8 产物里的新符号——`grep <新函数名> app/build/outputs/mapping/release/mapping.txt`（如 `repairIfEmpty`）。**另：用户报错日志里若带 `r8-map-id-<hash>`，先与本地 `mapping.txt`/APK dex 的 map id 比对**——一致即证明「用户跑的正是这个包」，可直接用本地 mapping 定位崩溃点。
11. **跨模块改动别按目录逐个 `git add`**（2026-10-09 实测踩到：`9bf375c54` 漏提交 workspace 模块 → 修于 `6421e9b81`）：workspace 侧新方法没提交，而 app 侧已在调用它 ⇒ **推送出去的版本编译不过**，本地却因为工作区里躺着那份改动**永远是绿的**——典型的"本地绿、远端红"。⇒ **定式**：`git add -A`（或显式列出**全部**受影响模块）之后用 `git status --short` 复核，**必须只剩无关的未跟踪文件**；只有「工作区干净 + 本地能编译」才等价于「远端那一版能编译」。顺带一个同源教训：生成代码/文档的脚本不幂等时，重跑会把同一段追加两遍（本批 `ReadFileWindow.kt` 就追加了两次策略块，靠编译报"Conflicting declarations"才发现）——脚本重跑前先确认上一次是否已落盘。

- **地基已具备（这是难度低的原因）**：①总占用/上限 → `Conversation.estimateWindowTokens()`（**usage 优先**且用压缩检查点判过新鲜度 + 真 tokenizer 兜底）+ `effectiveContextLength`（含用户覆盖）；②「有效历史 18 条 / 共 18 条」→ `PromptInspection.sentHistoryCount` / `totalMessageCount` **语义完全对应**（前者含压缩检查点算 1 条）；③组成明细 → `PromptInspector` 已按段给 token（`SYSTEM`/`CARD_SLOT`/`MEMORY`/`TOOL_GUIDANCE`/`TOOL_SCHEMA`/`RENDER_HINT`/`COMPRESSION_CHECKPOINT`/`TOOL_RESULT`/`INJECTION`/`CHAT_HISTORY`），且与实发路径共用 `PromptAssembly`（预览=实发）；④逐段 UI 已有整页「拼装预览」；⑤压缩入口（手动/自动/预设/检查点）齐备，估算已是压缩感知。**不需要动数据模型、压缩算法或发送链路。**
- **唯一真正要动脑的地方=口径自洽**：总占用是「usage 优先」，而拆分只能来自本地估算，两个来源不同的数并排会被用户当场核对 ⇒ 推荐**差值法**（历史 = 本地估算的有效历史；系统与记忆 = 总占用 − 历史），天然满足「两项相加 = 总数」；各段独立求和会出现加不平。
- **需要拍板的三件事**：①组成明细口径（建议差值法；并决定 `TOOL_SCHEMA`/`TOOL_RESULT` 这类是否单列一行——它们在实发里占比可能很大）②「轮数」定义（assistant 条？问答对？）与**样本不足时退化**（<3 轮不显示或写「样本不足」，文案必须带「约」，避免被当成承诺）③**三处入口的分工**（现有输入栏 tooltip、整页拼装预览，再加这个面板——别让三处讲同一件事）。
- **一处不照抄、一处已澄清**：①**不照抄其口径**——对方截图里「系统设定与记忆 **0 Tokens 0.0%**」：system 正文不可能为 0，说明其分段漏了 system，别继承；②圆环那个**黑色脏块是截图伪影**（用户已确认），**不是对方实现的问题** ⇒ 圆环可安心作为可选视觉项，只需定「替换现有细条还是并存」。

- **组成明细口径：已定差值法**（`系统与记忆 = 总占用 − 本地估算的有效历史`，保证相加=总数）；**但单列更多行时减数集合必须显式枚举在一处**（否则加不平），建议加一条「合计」对照行。

- **包名迁移**：fork 全线 `app.androidrik.*`（`material3` 子模块仍 `me.rerere`，预期）；cherry-pick 必须全局替换包名。

  `adb reverse tcp:8080 tcp:8080` 把**手机的** `127.0.0.1:8080` 转到本机，本机起一个假 SSE 服务
  （python stdlib 就够），App 里加一个临时提供商指向 `http://127.0.0.1:8080/v1`。
  **三个坑（都实测踩过）**：①**建提供商时 App 会自己打 `GET /v1/models`** 去拉模型，假服务必须答
  （否则建出来的提供商一个模型都没有，测不了）；②表单里 `添加 Key`/`添加` 等按钮标签**互为子串**，
  UI 自动化必须按**精确文本**匹配，否则会点错（我这次就多插了一行空 Key）；③**键盘弹出会让表单整体平移**，
  硬坐标必然打偏 —— 每次点击前**重新 dump 再点**，别复用上一轮的坐标。
  **用完必须清理三处**：临时提供商、被切过去的 `Assistant.chatModelId`
  （**模型选择器写的是 Assistant 字段、不是全局**，见 `ChatVM.setChatModel`）、测试会话。
- **假上游 + 自定义模型 ⇒ 请求里可能一个 `tools` 都没有（2026-10-16 实测）**：
  请求体里的 `tools` 只在 `model.abilities.contains(ModelAbility.TOOL)` 时才发
  （`ChatCompletionsAPI.kt:526`）。从假上游 `/v1/models` 建出来的临时模型**默认没有 TOOL 能力**，
  于是"假上游明明发了工具调用、App 也执行了"与"请求里 tools 是空数组"会同时成立 ——
  排查"提醒/护栏为什么没生效"时先看这一条（模型能力里把 TOOL 打开即可）。
  另注：`generateText(tools = …)` 那个参数是**助手侧的完整工具表**，与请求体里序列化出去的
  **不是一回事**（后者被模型能力过滤过）。
- **假上游 + 工具调用版（2026-10-16 补，复现「规则提醒/探索-落地守卫」时踩到的）**：让假上游**发工具调用**
  而不是只回文本时，多三个坑：①`delta.tool_calls[i].function.arguments` 是**字符串**不是对象；
  ②**无参工具（如 `get_time_info`）别连着发同样的调用** —— `toolCallSignature` 是「工具名+规范化参数」，
  同签名 3 次会先撞 `ToolCallLoopGuard` 优雅停止本轮、窗口永远填不满；塞一个多余的区分参数（`{"n":K}`）
  即可，**App 侧不做 schema 校验**，多余字段不被拦；③效果/护栏记录发生在**发起时**（不是成功时），
  所以工具执行失败的那轮**照样**填窗口 —— 要验"正常路径"就得真把工具启用，否则复现的是"失败尝试"形态
  （守卫行为一致，但报告里必须说清是哪一种）。另：**工具是否启用属于助手配置**，
  实测默认助手上 `get_time_info` 未启用会返回 `Tool xxx not found`，UI 里勾上即可（无需重建助手）。
