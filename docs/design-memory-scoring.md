# 记忆注入打分校准 + 预算截断（设计稿）

> 状态：**设计定稿，未实现**（2026-09-15，六项决策已全部确认见 §二）。
> 来源：Yuihub 记忆机制借鉴评估（`peer-apps-benchmark.md` §四）+ 与本仓代码/真实数据的逐条核对。
> 前序：`0580c6a6` 修了 `take(60)` 取最旧的缺陷（改取最新 60 条 + DAO 显式 `ORDER BY`）；本设计是它的下一步——从「取最新」升级为「取最该取」。

## 一、动机与现状核对

**表面动机**：Yuihub 用 `importance × 时效衰减` 打分 + 字符预算截断，比「取前 N 条」更合理。

**但核对本仓代码与真实数据后，问题重心与原先设想不同**：

当前常量（`GenerationPrompts.kt`）：

```kotlin
private const val MAX_MEMORY_INJECT_COUNT = 60        // 条数上限
private const val MAX_MEMORY_TOTAL_CHARS = 100_000    // 字符上限
```

实测设备记忆库（`backup_rikka_hub_20260914.db` 副本，2026-09-15）：

| 指标 | 值 |
|---|---|
| 条数 | 54 |
| 总字符 | 60,239 |
| 估算 token | ~43K（与真机实测「记忆 40.8K tokens 注入生效」吻合） |
| 中位 / 均值 / 最长 | 880 / 1116 / 3646 字符 |
| CJK 占比 | 62% |

**关键结论：两个上限都没触发 → 当前是「全量注入」**（54 条 < 60 条、60K < 100K），每次请求把全部记忆塞进 system prompt，约 4 万 token。所以：

1. `0580c6a6` 修的「取最新 60 条」在当前数据量下**根本没生效**；
2. 真正的行为变化不是「换排序」，而是**「砍到多少」**（预算从 100K 字符→一个真实预算）。

**条数上限不构成保护**：60 条与 token 量无关，记忆长度差异极大（最长 3646 = 中位 880 的 4 倍）。60 条按均值≈6.7 万字符（≈4.8 万 token），按最长可达 21.9 万字符——所以**必须改成 token/字符预算截断**，条数上限管不住体积。

## 三、预算取值（决策 #1 展开）

照搬 Yuihub `PROMPT_MEMORY_CHAR_BUDGET = 1800` 的后果（实测本仓数据，贪心小件优先=最优装箱）：

| 预算（字符） | 保留条数 |
|---|---|
| 1800 | 7 / 54（13%） |
| 4000 | 13 / 54（24%） |
| 8000 | 20 / 54（37%） |
| 16000 | 30 / 54（56%） |
| 100000（现状） | 54 / 54（100%） |

**1800 会让 87% 的记忆离开上下文**——对已积累 54 条的用户是行为剧变，不是微调。Yuihub 的 1800 约合 600 token，适合它的使用模式，不应照搬。

**定案**：预算按 **token** 计，**起步区间 5K–10K token**（对应 54 条这份数据约 16K–32K 字符、装下 30–45 条）。真正的收益区间是「从 4 万 token 降到几千」，再往下边际收益小、丢记忆风险陡增。实现时在该区间取一个具体初值，之后按可调参数调。

第二条上限（`MAX_MEMORY_TOTAL_CHARS = 100_000`）与新预算**功能重叠**，实现时应合并为单一预算参数，避免两套上限打架。

## 四、importance 从哪来（决策 #2 展开）

**打分校准的公式是 `importance × 时效衰减`。若不要 importance，公式退化为纯时效衰减 = 等价于现在的「取最新」= 白做。** 所以这个字段是整套设计的承重墙。

**定案：模型在工具调用时填 + 用户在记忆页可覆盖。**

**为什么不是「仅用户手动填写」**（该提案曾提出，最终未采纳）：

1. **记忆的主要产生者是模型**（`memory_tool` 的 create/edit 走工具调用）。纯手动填意味着每条新记忆都要去记忆页补分，否则全落默认值 → 打分退化为纯时效衰减 = **等于白做**；
2. 模型一轮可能建多条（实测一次建 6 条），逐条补分不现实；
3. **写入那一刻，模型比用户更清楚该打几分**——「这是身份信息还是次要偏好」正是模型在上下文里能判断的。用户可覆盖已保留最终决定权。

**实现**：

- 工具 schema 加 `importance` 参数 + 描述引导分档（照 Yuihub：0.9+ 身份/强偏好、0.6–0.8 普通偏好/进行中项目、0.2–0.5 次要）；create/edit 都支持；
- 记忆页编辑对话框加该字段（已有编辑对话框，加一个输入即可）；缺省回退 0.6。

**风险（实现后才知，需真机验证）**：模型可能普遍给 0.9（都重要）或干脆不填（全落默认）——若如此，importance 退化为噪声，不如不要。靠工具描述里的明确分档示例压制，效果取决于模型。**这是本设计最不确定的一环**。

## 五、排序稳定性：分档量化（决策 #3 展开）

**问题**：记忆注入在 system prompt 里=**前缀**。当前按 `sortKey`（自增主键）排序，不增删记忆时选择结果稳定 → 前缀稳定 → 缓存命中。引入时效衰减后**排序随时间漂移**：

- 记忆 A：importance 0.9，60 天前更新 → `0.9 × (0.55 + 0.45×0.25)` = 0.596
- 记忆 B：importance 0.6，刚更新 → `0.6 × 1.0` = 0.600 → **B 暂时排 A 前**
- 再 60 天：B 衰减到 0.398、A 到 0.52 → **A 反超**

翻转本身无害，但**若发生在预算截断边界上**，入选集合变化 → system prompt 变化 → 前缀缓存失效。这触及 `design-auto-compaction.md` 立的「前缀字节稳定」约束。

**定案：分档量化**——score 量化为桶（如 0.1 一档），**桶内按 id 稳定排序**，边界抖动只在跨桶时发生，月级翻转的冲击基本消除。

## 六、tokenizer：复用现有启发式（决策 #4 展开）

**本仓已有一个**（原以为需新引入）：`utils/ContextLength.kt:62`

```kotlin
return (cjk / 1.5 + other / 4.0).toInt()   // CJK 1.5 字符/token，其余 4 字符/token
```

已被压缩规划器（`CompressionPlanner`）与上下文占用（`estimateWindowTokens`）使用。

**定案：复用，不引依赖（「目前」先这样）。** 它是启发式（误差约 ±20%），但对「决定装几条记忆」足够——不需要精确计数，只需要可比量纲。**注意本仓已有实现**（提出「引入 tokenizer」时不知道这点），所以这条的实际选择是「复用已有」vs「替换成真词表」，而非「有/无」。将来要换的成本与陷阱见 §6.1。

**小重构**：它入参是 `List<UIMessage>`，记忆是纯字符串 → 需抽 `String` 重载（或抽 `estimateTokens(text: String)` 让两者共用）。

### 6.1 后续若引入真 tokenizer 的成本（探讨结论）

**成本低，前提是守住三条**——因为估算值现在是**纯瞬态**的：

- `estimateTokenCount` 是纯函数，调用方当场算当场用；
- 唯一落库的 token 数是 `usage.promptTokens`（**供应商返回的真实 usage**，`MessageNodeDAO.kt:140` 从消息 JSON 提取），与启发式估算无关；
- `CompressionCheckpointEntity` 只存 `boundaryNodeId` 等结构信息，**不存 token 估算**；
- Settings 里的 `contextLengthOverride`/压缩阈值存的是**窗口大小与阈值**（配置），不是对文本的估算结果。

所以换 tokenizer = **换一个函数实现**，调用点全不用动，无迁移无回填。

**三个必须避开的陷阱**：

1. **不要把估算结果存进 `MemoryEntity`（或任何表）**。为"性能"缓存 `tokenCount` 列 → 换 tokenizer 时该列全是旧算法的错值，要么迁移重算、要么带错跑。**token 数必须每次现算**（记忆几十条、每条千字符级，开销可忽略；Yuihub 甚至放在 `Dispatchers.Default`）。`compression_checkpoint` 同理。
2. **预算常量别与具体 tokenizer 绑定**。写死 `5000` 并附注"按 cl100k 算" → 换词表后含义漂移。预算应作为**可调参数存 Settings**（同 `contextLengthOverride` 待遇），换时重新调。
3. **`estimateTokenCount` 是三个消费者共享的**（记忆预算 / 压缩切分点 `CompressionPlanner` / 占用进度条 `estimateWindowTokens`）。换它会**同时改变压缩行为**——同样的对话可能因"更准了"而提前/延后触发。这不是 bug，但换的时候要有意识：**是全局口径变更，不是局部替换**。

**真 tokenizer 的现实麻烦**（提前知道）：

- **没有通用 tokenizer**：cl100k/o200k 是 OpenAI 的，Claude 与 Gemini 各不同。fork 多供应商 → 要么按 model 选词表（`Model` 现在**无任何 tokenizer/encoding 字段**，需新增映射），要么继续用一个近似（又回到启发式）。**按 provider 选词表是"真准确"与"工程复杂度"的分水岭**。
- **体积**：jtokkit 词表数据 MB 级 asset，会让 APK 变大。

**结论**：现在用启发式、保持瞬态，是正确中间态。真 tokenizer 的收益（±20%→±2%）对"装几条记忆"很小，成本（依赖+体积+per-provider 映射）实打实。**值得换的时机 = 估算误差开始导致可观察问题**（占用条明显不准、压缩该触发没触发）——在那之前，误差被"预算留余量"轻易吸收。

## 七、回收站（决策 #5 展开，建议单独一轮）

**方向同意**：`delete` 不可逆，与 `memoryModifyApproval` 默认拦 edit/delete 的逻辑同源（不可逆所以要拦）。

**但建议与打分校准分开做**——两者动同一张表和同一批查询，混做会让下面两个坑互相纠缠：

**① 与 200 条上限的交互会出错。** 现超限删最旧（`MemoryRepository.kt:120`）。软删后：

- 软删的**算不算** 200 条之内？算 → 回收站挤占配额、把活跃记忆挤出去；不算 → 计数查询要加 `WHERE deleted_at IS NULL`，而 `getMemoriesOfAssistant` 被**注入、UI、幂等检查三处共用**，改语义波及全部。

**② 幂等检查会误判「复活」。** `addMemory` 靠「同内容已存在则复用」去重（治工具循环重复创建）。软删后若回收站有同内容记忆，新建会判为"已存在"而复用一条**用户已删除的**记忆 → 被删记忆静默复活。

**③ 「删助手」路径绕过回收站**：`AssistantVM.kt:54` 删助手时调 `deleteMemoriesOfAssistant` 硬删。合理（助手没了回收站给谁看），但需在设计里写明，否则会被当成漏改。

**④ 范围问题**：回收站 per-assistant 还是全局？记忆有 `assistantId` 与 `__global__` 两种作用域，UI 要处理。

实现注意：超限淘汰策略应同步改为**按分数淘汰**（与入选口径一致），否则 200 条上限处会出现「重要老记忆被不重要的新记忆挤掉」。

## 八、实现骨架（建议顺序）

1. **DB 28→29**：`MemoryEntity` 加 `importance`（默认 0.6）+ `updatedAt`（默认 0 或 `createdAt`）；（回收站轮再加 `deleted_at`）。参照 `Migration_27_28` 的纯 `ALTER TABLE ADD COLUMN` 手法。
2. **`updatedAt` 必须随 edit 更新**——否则改过的记忆仍按旧时间衰减。
3. **`estimateTokenCount` 抽 `String` 重载**，与既有 `List<UIMessage>` 版共用口径。
4. **打分函数**：`importance × (0.55 + 0.45 × exp(-ln2 × age / 30天))`，`age` 基于 `updatedAt ?: createdAt`；分档量化后桶内按 id 排。
5. **预算截断**：超预算时**跳过该条并继续**（`continue` 而非 `break`），否则一条长记忆会堵死后续预算；注意防「第一条就超预算 → 返回空」（条件加 `selected.isNotEmpty()`）。**此细节照抄 Yuihub**——本仓最长 3646 字符，在 8K 预算下差异明显。
6. **工具 schema**：`importance` 参数 + 分档描述（create/edit 都支持）。
7. **用户可覆盖**：记忆页编辑对话框加 importance 字段。
8. **预算存 Settings**（不硬编码），与 `contextLengthOverride` 同待遇。
9. **单测**：打分单调性/分档稳定性（顺序不随时间抖动）/预算截断不堵死/`updatedAt` 随 edit 更新/importance 缺省回退。

**预计 1–2 提交**（不含回收站）。
