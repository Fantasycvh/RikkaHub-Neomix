> 关联：`docs/handoff-2026-09-04.md`（issue 跟踪节）、备份打包前缀事故（同类「约束散落多处必漂移」教训）。

## 一、决策（已定，不再讨论）

| # | 决策点 | 定论 |
|---|---|---|
| 1 | 新会话落点 | **顶部最前**（即所在档位的最前） |
| 2 | 与置顶的关系 | **两档并存**：置顶 = 第一档，非置顶 = 第二档；**档内**按自定义顺序。不合并成一套 |
| 3 | 信息补偿 | 列表行内**显示最近活跃时间**＝**末尾消息的 `createdAt`**（不用 `update_at`：它会被改标题/置顶/重新生成等非消息动作刷新，正是 issue 抱怨的"只是编辑一下就被顶到最前"） |
| 4 | 拖拽入口 | **「编辑顺序」模式**：进入后长按即拖，退出即锁定（不常驻拖拽手柄；会话行长按已用于菜单，见 §六） |
| 5 | 位置编码 | **整数大间距**（1000 / 2000 / …），插入取中值；间距耗尽时**一次性归一化**；起始值 `1_000_000`（留双向余量） |
| 6 | 置顶时的位置 | **保留原 `sortOrder` 不动**（置顶只换档显示；取消置顶回到原相对位置 = 最小意外）。代价是"置顶后可能落在置顶档中间"，**须在 UI 上提醒**（见 §四.2） |
| 7 | 时间档排序 | **不再提供**（顺序已由用户定义，"列表跳动"从根上消失）；保留**「恢复默认顺序」**入口（清空该档 `sortOrder` → 回到按更新时间，即现状行为） |
| 8 | AI「最近对话」工具 | **保持按时间**（语义是"最近"，与用户排序无关）；抽屉/历史页/文件夹/Web API 统一走用户排序 |

## 二、位置编码的细节（据 §一.5 展开）

- 列：`ConversationEntity.sortOrder: Long?`（**可空**，null = 从未手动排过）。
- 归一化档位：**档内**（置顶档 / 非置顶档各自独立编号空间；两档之间不比较）。
- 分配规则：
  - **新会话置顶**：`min(该档所有 sortOrder) - 1000`。
  - **拖拽落点**：取前后邻居的中值 `(prev + next) / 2`。
  - **间距耗尽**（`next - prev <= 1`）：提交时对该档**整段重写**为 `1_000_000, 1_001_000, 1_002_000, …`（一个事务）。
  - **首条**：从 `1_000_000` 起（向上向下各留约 10^15 / 10^12 次操作余量，实际永不触界）。
- 为什么用整数而非浮点：定点写回、**无精度零头**、日志/备份里可读；代价只有「间距耗尽」，而它的触发时机完全可预测（同一间隙连续取中值约 10 次）。

## 三、实现约束（原「实现前待定项」，已全部确认）

1. **`sortOrder` 的写入点必须唯一**：至少两条路径会改顺序——①拖拽提交（「编辑顺序」模式）②**新会话置顶分配**（发首条消息时）；Web API 也可能创建会话 ⇒ 单点 `allocateSortOrder(tier)` / `applyOrder(tier, movedIds)`，且**在同一事务内**先读档位极值再写。否则并发下会分配出相同值（同值退化成时间序，表现为"偶尔拖不动"）。
2. **置顶/取消置顶保留原值**（§一.6），并且**必须在 UI 提醒**（见 §四.2）。
3. **「最近活跃」取末尾消息的 `createdAt`**（§一.3）；消息未完成时用其 `finishedAt ?: createdAt` 不必要——列表只读不必与生成态耦合，取 `createdAt` 即可。
4. **排序表达式必须单点收敛**：`ConversationDAO` 现有 **11 处**硬编码 `ORDER BY is_pinned DESC, update_at DESC`，另有分页查询在用 Room 生成的 `PagingSource`（**不支持 `@RawQuery`**）。经**编译验证**：Room **允许**在 `ORDER BY` 用绑定参数
   （`ORDER BY is_pinned DESC, CASE WHEN :byCreated THEN create_at ELSE update_at END DESC` 编译通过）。自定义顺序落地时同样单点生成排序子句 + 加**护栏测试**（防止将来加档时只改一处）。文本类排序不能与数值混在同一 CASE（SQLite 按类型比较），必要时写成独立查询。
5. **归一化的作用域与时机**：只重写**受影响档位**（不是全表）；只在**提交时**（拖拽结束 / 新会话分配后发现耗尽）触发，**绝不在拖拽过程中改数据**。整段重写的行数 = 该档会话数（几十到几百），一个事务足够。

## 四、UI 要求

1. **「编辑顺序」模式**：入口建议放在会话列表顶部（抽屉/历史页）的溢出菜单；进入后：
   - 长按即拖（`sh.calvin.reorderable` 已是本仓依赖，模型列表 / 助手列表两处有成熟用法）；
   - 顶部一条说明：**"拖动调整顺序；置顶分档不受影响，取消置顶会回到原来的位置"**；
   - 退出即锁定（返回键 / 完成按钮），模式状态不持久化（下次进入仍是浏览态）。
2. **置顶不改变档内位置的提醒**（用户要求，落在两处）：
   - 「编辑顺序」模式内的常驻说明（上条）；
   - 长按菜单点「置顶」后的 toast：「已置顶（保持原顺序位置）」；点「取消置顶」后：「已取消置顶（回到原位置）」。
     —— 用户既不惊讶于"置顶后没跑到最前"，也知道取消置顶不会丢失排序。（文案 6 语言）
3. **行内最近活跃时间**：会话行显示**末尾消息 `createdAt`**（相对时间即可，与现有时间格式保持一致）。
4. **「恢复默认顺序」**：入口建议与「编辑顺序」同处；语义 = 清空该档 `sortOrder`（回到按更新时间），操作前确认对话框（不可撤销的一次性重排）。

## 五、落地步骤（排期时按此拆）

1. schema：`sortOrder: Long?` + AutoMigration（`AppDatabase` 版本 +1，模式见 DB v32 的 knowledge 表）。
2. 排序中心化：单点排序子句生成 + 11 处查询收敛 + 护栏测试（防漂移）。
3. 档内顺序的读写：`allocateSortOrder` / `applyOrder` / `normalizeTier`（含并发同值防护）。
4. UI：§四 四项（编辑顺序模式、置顶提醒、行内时间、恢复默认顺序）。
5. 多视图一致性：抽屉、聊天历史页（分页）、文件夹视图、Web API 统一走同一排序函数；AI「最近对话」工具保持按时间。

## 六、成本与风险

- 估时：**1.5–2 天**（含迁移、排序中心化、拖拽模式、归一化与护栏测试、真机验证）。
- 主要风险不在代码，而在**语义**：顺序由用户掌控后，"新消息把会话顶上来"这一默认直觉消失 ⇒ 靠 §一.1（新会话顶部最前）+ §一.3（行内末尾消息时间）两处补偿；「恢复默认顺序」是兜底退路。
- 交互风险：长按已用于会话菜单（`ExpressivePopup`：置顶 / 重新生成标题）⇒ 拖拽必须走「编辑顺序」模式，**不能**直接绑长按，否则两者冲突（这是 §一.4 的由来）。
