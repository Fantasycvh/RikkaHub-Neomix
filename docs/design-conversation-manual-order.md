> 关联：`docs/handoff-2026-09-04.md`（issue 跟踪节）、备份打包前缀事故（同类「约束散落多处必漂移」教训）。

## 一、决策（已定，不再讨论）

| # | 决策点 | 定论 |
|---|---|---|
| 1 | 新会话落点 | **顶部最前**（即所在档位的最前） |
| 2 | 与置顶的关系 | **两档并存**：置顶 = 第一档，非置顶 = 第二档；**档内**按自定义顺序。不合并成一套 |
| 3 | 信息补偿 | 列表行内**显示最近活跃时间**（`update_at` 不再决定顺序，用户仍要看得出"最近聊过哪条"） |
| 4 | 拖拽入口 | **「编辑顺序」模式**：进入后长按即拖，退出即锁定（不常驻拖拽手柄） |
| 5 | 位置编码 | **整数大间距**（1000 / 2000 / …），插入取中值；间距耗尽时**一次性归一化** |

## 二、位置编码的细节（据 §一.5 展开）

- 列：`ConversationEntity.sortOrder: Long?`（**可空**，null = 从未手动排过）。
- 归一化档位：**档内**（置顶档 / 非置顶档各自独立编号空间；两档之间不比较）。
- 分配规则：
  - **新会话置顶**：`min(该档所有 sortOrder) - 1000`。
  - **拖拽落点**：取前后邻居的中值 `(prev + next) / 2`。
  - **间距耗尽**（`next - prev <= 1`）：提交时对该档**整段重写**为 `1000, 2000, 3000, …`（一个事务）。
  - **首条**：从 `1_000_000` 起（或 `0`），留出双向余量。
- 为什么用整数而非浮点：定点写回、**无精度零头**、日志/备份里可读；代价只有「间距耗尽」，而它的触发时机完全可预测（同一间隙连续取中值约 10 次）。
- 边界：起始值若为 `0`，反复「新会话置顶」从 0 递减到 `Long.MIN_VALUE` 需约 9×10^15 次操作——实际上永不发生；仍建议起始值给 `1_000_000` 以便两个方向都不易触界。

## 三、我必须提醒的实现前决策点（5 处，建议实现时一并定）

1. **`sortOrder` 的写入点必须唯一**：至少两条路径会改顺序——①拖拽提交（「编辑顺序」模式）②**新会话置顶分配**（发首条消息时）。加上 Web API 也可能创建会话 ⇒ 需要一个单点
   `allocateSortOrder(tier)` / `applyOrder(tier, movedIds)`，且**在同一事务内**读当前档位极值后再写，否则并发下会分配出相同值（同值时的次序会退化成时间序，表现为"偶尔拖不动"）。
2. **置顶/取消置顶时 sortOrder 怎么处理**——建议**保留原值不动**：置顶只是换个档位显示，取消置顶后回到原来的相对位置（最小意外）。若保留，则"置顶后它出现在置顶档的中间"是正常现象（因为它的旧值可能就在中间）。反之若希望置顶后落在置顶档最前，需在置顶时重新分配 `min(置顶档) - 1000`。**这条我倾向保留原值**，但需要你确认。
3. **「最近活跃时间」取哪个时间**：`update_at` 会被**非消息动作**刷新（改标题、置顶、重新生成等，正是 issue 作者抱怨的"只是编辑一下就被顶到最前"）。若要如实表达"最近聊过"，建议显示**末尾消息的 `createdAt`**（或已完成的 `finishedAt`），而不是 `update_at`。
4. **ORDER BY 的收敛（必须做，否则必然漂移）**：`ConversationDAO` 现有 **11 处**硬编码 `ORDER BY is_pinned DESC, update_at DESC`，另有分页查询在用 Room 生成的 `PagingSource`（**不支持 `@RawQuery`**）。经编译验证：Room **允许**在 `ORDER BY` 用绑定参数
   （`ORDER BY is_pinned DESC, CASE WHEN :byCreated THEN create_at ELSE update_at END DESC` 编译通过）。自定义顺序落地时同样应**单点生成排序表达式**（值排序），并加护栏测试；文本类排序不能与数值混在同一 CASE（SQLite 按类型比较），必要时写成独立查询。
5. **归一化的作用域与时机**：只重写**受影响档位**（不是全表）；只在**提交时**（拖拽结束/新会话分配后发现耗尽）触发，绝不在拖拽过程中改数据。整段重写的行数 = 该档会话数（通常几十到几百），一个事务足够。

## 四、与「排序档」（issue 原始建议）的关系

自定义顺序落地后，**时间档排序不再需要**：顺序由用户定义，「列表随 update_at 跳动」的问题从根上消失。
但建议保留一个 **「恢复默认顺序」** 入口（清空该档 `sortOrder` → 回到按更新时间，即现状行为），
给"拖乱了想重来"的用户一条退路。

## 五、落地步骤（排期时按此拆）

1. schema：`sortOrder: Long?` + AutoMigration（`AppDatabase` 版本 +1，模式见 DB v32 的 knowledge 表）。
2. 排序中心化：`conversationOrderBy(tier/mode)` 单点 + 11 处查询收敛 + 护栏测试（防漂移）。
3. 档内顺序的读写：`allocateSortOrder` / `applyOrder` / `normalizeTier`（含并发同值防护）。
4. UI：「编辑顺序」模式（进入后长按即拖；`sh.calvin.reorderable` 已是本仓依赖，模型列表/助手列表两处有成熟用法）+ 行内最近活跃时间 + 「恢复默认顺序」。
5. 多视图一致性：抽屉、聊天历史页（分页）、文件夹视图、Web API 统一走同一排序函数；AI 的「最近对话」工具**保持按时间**（语义是"最近"，与用户排序无关）。

## 六、成本与风险

- 估时：**1.5–2 天**（含迁移、排序中心化、拖拽模式、归一化与护栏测试、真机验证）。
- 主要风险不在代码，而在**语义**：顺序由用户掌控后，"新消息把会话顶上来"这一默认直觉消失 ⇒ 靠 §一.1（顶部最前）+ §一.3（行内时间）两处补偿；「恢复默认顺序」是兜底退路。
- 交互风险：长按已用于会话菜单（`ExpressivePopup`：置顶 / 重新生成标题）⇒ 拖拽必须走「编辑顺序」模式，**不能**直接绑长按，否则两者冲突（这是 §一.4 的由来）。
